# CLAUDE.md — Строгие инструкции для Claude Code (и любого другого агента)

Этот файл имеет наивысший приоритет в проекте.
Все предыдущие договорённости, чат-история и память сессии игнорируются, если они противоречат этому файлу.
Ты обязан следовать этим правилам в каждом ответе и каждом действии.

## 1. Beads (`bd`) — единственный источник правды и долгосрочной памяти

**Абсолютное правило №1**

Всё планирование, трекинг задач, сохранение контекста, декомпозиция, статусы — только через `bd`.

Запрещено:
- хранить TODO в markdown файлах
- писать «запомни это»
- держать списки задач в чате
- полагаться только на историю сообщений
- Запрещено изменять код, если статус задачи в bd не in_progress

Каждая новая сессия начинается одинаково:

```bash
bd sync              # синхронизируем граф с git/dolt
bd doctor --fix      # чиним любые проблемы автоматически
bd ready --json      # это ТВОЙ единственный to-do list на сейчас
```

Если `bd ready` пуст — говори пользователю:

> Нет готовых (unblocked) задач. Нужно либо создать новую, либо разблокировать существующие. Что делаем?

## 2. Как правильно создавать и называть задачи

Название задачи — 70–80% контекста.
Название должно быть самодостаточным: человек, открывший `bd list` через 3 месяца, должен сразу понять, о чём задача.

Шаблон хорошего названия:

```text
<ветка/эпик>: <что именно делаем> в <файл/модуль> — <краткий текущий контекст/проблема>
```

Префикс в названии задачи обязан совпадать с названием текущей git-ветки

Примеры для проекта `simpleAI`:

- `task/simpleAI-mpy-logging: Добавить mp_log_debug в py/runtime.c вместо printf`
- `task/simpleAI-mpy-logging: Реализовать уровни логирования (DEBUG/INFO/ERROR) в py/mpconfig.h`
- `task/simpleAI-mpy-logging: Перенаправить все mp_printf вызовы на mp_log в py/obj.c`
- `task/simpleAI-mpy-logging: Добавить timestamp и task name в mp_log (ESP32 FreeRTOS)`
- `task/simpleAI-mpy-logging: Написать тест на переполнение лога в mpy-heap-limited режиме`

Описание (`--description`) всегда включает:

- текущую ветку
- файлы/модули, которые затрагиваются
- что уже сделано в предыдущих bd-задачах
- acceptance criteria (как понять, что задача решена)
- важные нюансы (архитектура, ограничения памяти, конкретное железо)

Пример команды создания:

```bash
bd create "task/simpleAI-mpy-logging: Добавить mp_log(level, fmt, ...) в py/runtime.c" --type task --priority 2 --description "Текущая ветка: task/simpleAI-mpy-logging
Затрагиваемые файлы: py/runtime.c, py/mpconfig.h
Уже сделано: bd-17 — базовый mp_log без уровней
Требуется: функция mp_log с уровнями DEBUG/INFO/WARN/ERROR/CRITICAL
Acceptance: все printf в runtime заменены на mp_log, логи видны в UART, уровень можно отключить #define
Ограничения: не больше 128 байт на сообщение, работает на ESP32 и RP2040"
```

## 3. Структура проекта в beads
 - Принцип: Один Эпик = Одна ветка.
 - При создании Эпика агент обязан убедиться, что он в новой ветке от dev, или создать её: git checkout -b task/simpleAI-name dev.
 - Типы:
   - Эпики — крупные цели (`type: epic`).
   - Задачи — атомарные куски (`type: task`, длительность 5–45 минут).
 - Блокировки — жёстко используй `depends` и `blocks`.

```bash
bd depends 42 43          # 43 блокирует 42 (42 ждёт 43)
bd depends --parent 10 42 # 42 входит в эпик 10
```

Типичный эпик выглядит так:

- Эпик 10: `task/simpleAI-mpy-logging: Полноценная система логирования в MicroPython`
- 11: `Добавить структуру уровней в mpconfig.h`
- 12: `Реализовать базовую функцию mp_log`
- 13: `Заменить все printf → mp_log в runtime`
- 14: `Добавить timestamp и thread-id (FreeRTOS)`
- 15: `Реализовать буферизацию логов (чтобы не терять при переполнении UART)`
- 16: `Тесты на разных уровнях логирования`
- 17: `Документация в README-mpy-logging.md`

## 4. Рабочий цикл агента (строго соблюдать)

1. `bd sync && bd doctor --fix`
2. `bd ready` → берём самую приоритетную готовую задачу
3. Убедиться, что текущая git-ветка соответствует префиксу задачи. Если нет — переключиться или сообщить пользователю
4. `bd update <id> --status in_progress --claim`
5. Пишешь план действий (если задача > 15 мин)
6. Делаешь изменения
7. Коммитишь с номером задачи: `git commit -m "task/simpleAI-mpy-logging: добавить mp_log в runtime.c (bd-42)"`
8. `bd update <id> --status done` или `bd close <id>`
9. В конце каждого ответа/сессии обязательно:
```bash
    bd sync
    git status # Проверить, что все изменения закоммичены локально
```

```text
Закрыто: bd-42, bd-43
В работе: bd-44
Следующая готова: bd-45 (добавить timestamp в лог)
```

## 5. README — обязательно обновлять после каждого коммита

После каждого коммита (или серии коммитов в рамках одной задачи) README.md **обязан** отражать актуальное состояние проекта.

README должен содержать:
- **Архитектуру**: кто за что отвечает, как компоненты связаны между собой
- **Структуру каталогов**: все `cmd/`, `internal/` пакеты с кратким описанием
- **Как запустить каждый компонент**: конкретные команды, переменные окружения
- **Поток данных**: как запрос проходит от пользователя до ответа
- **Зависимости**: что нужно поднять перед запуском (DB, переменные и т.д.)

Правило простое: человек, который забыл всё про проект, открывает README и через 5 минут понимает структуру, умеет запустить и знает куда смотреть.

Запрещено:
- коммитить без обновления README если изменилась структура, новые команды, новые архитектурные компоненты
- держать в README устаревшую информацию

## 6. Запреты и антипаттерны

- Никогда не используй `bd edit` (ты не можешь открыть редактор)
- Запрещено смешивать задачи разных Эпиков в одной ветке
- Не пиши большие куски кода без создания задачи
- Не используй чат как замену beads
- Не создавай задачи без префикса ветки/эпика

## 7. Экстренные команды

```bash
bd quickstart          # если граф сломался
bd list --blocked      # посмотреть, что застряло
bd list --stale        # старые незакрытые задачи
bd cleanup --days 60   # убрать древние завершённые
bd hooks install       # поставить git-хуки (commit-msg и т.д.)
```
