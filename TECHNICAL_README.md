# Technical README (RU)

Этот файл — живой технический контекст проекта. Здесь фиксируем цели,
планы, сделанное, риски и архитектурные решения. Обновляйте после
существенных изменений.

## Видение
Построить модульную платформу агента, к которой можно удобно подключать
новые функции (проверка бюджета, аудит почты, обработка чеков и т.д.) с
понятными интерфейсами, безопасным исполнением и устойчивым хранением
контекста.

## Текущее состояние
- CLI‑агент читает ввод из stdin и отправляет запрос в LLM.
- Конфиг и логирование вынесены отдельно.
- Добавлен Docker‑контейнер Postgres с pgvector и миграции goose.
- Ingestion: чек + позиции + RAG документы.
- RAG: генерация эмбеддингов и retrieval по векторам.
- Telegram‑бот: текст + сохранение вложений, базовые ограничения.
- Telegram ingestion: сохраняет входной payload в `TELEGRAM_MEDIA_DIR`.

## Ближайшие цели

## План: RAG по тратам и чекам
Фокус — хранение трат в БД, векторизация и подача контекста в LLM.

1) Определить схему данных:
   - Покупка, чек, магазин, категория, валюта, дата/время, источник.
   - Минимальный набор полей и формат нормализации.
2) Выбрать хранилище:
   - БД (Postgres) и векторное хранилище (pgvector или отдельный сервис).
   - Решить, где хранить сырой текст чеков и артефакты.
3) Интеграция приема данных:
   - Telegram‑бот как вход: текст, фото, файлы.
   - Парсинг чеков, валидация, дедупликация.
4) Индексация и RAG:
   - Формирование документов, метаданные и фильтры.
   - Политика переиндексации.
5) Подключение к агенту:
   - Retrieval по запросу, лимит контекста, шаблоны промпта.
6) Тесты и наблюдаемость:
   - Тесты парсинга и RAG‑выборки.
   - Логи ошибок и базовые метрики.

## План: агент почты (multibox, hourly)
Цель — раз в час собирать новые письма из нескольких ящиков и слать
единый дайджест в Telegram, разделенный по аккаунтам.

### Решения
- Провайдеры: Gmail API + IMAP XOAUTH2 (iCloud, Яндекс).
- Хранение токенов: .env (без БД), ротация вручную.
- Канал доставки: Telegram (один общий).
- Формат: секции по аккаунтам.

### Архитектура
- Новый воркер: `cmd/worker` с тикером раз в час.
- Модуль почты: `internal/mail` с интерфейсом провайдера.
- Доставка: `internal/notify` (Telegram).
- Состояние: таблицы `mail_account`, `mail_message`, `mail_checkpoint`, `mail_run`.

### Этапы
1) Конфиг:
   - Массив аккаунтов (provider, email, tokens, labels/folders).
   - Telegram токен и chat_id.
2) Хранилище:
   - Схемы таблиц, миграции и модель данных.
   - Дедупликация по Message‑ID/UID.
3) Интеграции:
   - Gmail API (OAuth token).
   - IMAP XOAUTH2 (iCloud, Яндекс).
4) Pipeline:
   - Чтение новых писем с момента checkpoint.
   - Нормализация (from, subject, date, preview).
   - LLM‑оценка важности/категории (important/normal/ignore).
   - Фильтрация/сортировка по важности.
   - Группировка по аккаунтам, summary через LLM.
   - Отправка в Telegram.
5) Наблюдаемость:
   - Логи run‑сессий, ошибок, пустых итераций.
   - Метрики count писем/аккаунтов.

- Мигратор: goose.
- Локальный запуск: `make db-up`, миграции: `make migrate-up`.

## Ingestion (v1)
- Команда: `go run cmd/ingest/main.go -file receipt.json`
- Вход: JSON с сырым текстом и нормализованными позициями.
- Выход: сохраняет `receipt`, `receipt_item` и `rag_document` (без эмбеддингов).

Пример JSON:

```json
{
  "source": "telegram",
  "source_ref": "msg:123",
  "purchase_ts": "2026-01-24T12:00:00Z",
  "currency": "RUB",
  "total_amount": 1000.00,
  "store_name": "Пятерочка",
  "raw_text": "Чек: мука 1000гр 1000р",
  "items": [
    {
      "name": "Мука",
      "quantity": 1.000,
      "unit_price": 1000.00,
      "amount": 1000.00
    }
  ]
}
```

## RAG: эмбеддинги
- Модель: `text-embedding-3-small`.
- Размер вектора: 1536 (соответствует `vector(1536)` в схеме).
- Команда (v1): `go run cmd/embeddings/main.go -limit 100 -batch 20`

## Хранение сырого текста и артефактов
- `receipt.raw_text` хранит полный текст чека.
- Вложения (фото/сканы) храним вне БД, в БД сохраняем ссылки в `receipt_artifact`.

## RAG: шаблоны контента
- Receipt: `Receipt | store={store} | ts={purchase_ts} | total={total} {currency} | items={item_count}`
- Item: `Item | name={name} | qty={qty} | unit={unit_price} | amount={amount} {currency} | category={category_name}`

## RAG: pipeline (high level)
1) Ingestion: получаем сырой текст чека, валидируем и сохраняем `receipt`.
2) Normalization: извлекаем позиции, итоги, валюту и сохраняем `receipt_item`.
3) Document build: создаем `rag_document` для чека и каждой позиции.
4) Embeddings: генерируем векторы и сохраняем в `rag_document.embedding`.
5) Retrieval: ищем по вектору + фильтрам и подставляем в контекст LLM.

Команда (v1):
`go run cmd/rag-query/main.go -q "сахар в январе" -limit 5`

## RAG: переиндексация (v1)
- Переиндексируем документ, если `embedding` отсутствует.
- Переиндексируем документ, если `content_hash` отличается от нового контента.
