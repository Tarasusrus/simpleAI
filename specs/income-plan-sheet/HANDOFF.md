# HANDOFF: План окна (эпик simpleAI-766e) — состояние на 2026-10-17

Прочитай целиком до любых действий. Затем: `bd show simpleAI-766e`, `bd ready --allow-stale`, `git status`, CONTEXT.md (последняя сессия).

## Что за проект
Экран «план окна» для владельца (один человек, Таиланд, зарплата/аванс ~раз в 2 недели) плюс Telegram-бот на одном общем расчёте. Окно = 14 дней от поступления (факт или ожидаемое); главное число «Можно тратить до конца окна» (= поступления − платежи − факт − резерв), «в день», лента платежей, «следующее окно», «позже» по месяцам, «без даты» (вне расчёта), «Как обычно тратишь». Принципы: SOLID, DRY, KISS, YAGNI; логика только в Go (BFF), фронт рисует готовое; Telegram и экран — два интерфейса одних данных.

## Что сделано и РАБОТАЕТ НА ПРОДЕ
- Фаза 1: чистый домен `internal/plan` (даты, деньги целыми, повторы, окна, расчёт). Спека: specs/income-plan-sheet (requirements, constraints C1–C45, domain-types, contract.md, mockup.html), ADR-009.
- Миграция 00021 (прод на версии 21): новые колонки правил повтора, плановых записей, транзакций, таблица plan_settings. Откат: Down с отказом при новых данных; ручной deploy/rollback-00021.sql. Читатели бота отфильтрованы (direction/amount), `GetDueRecurring` берёт только расходы, `AddRecurring` пишет обе группы колонок.
- Чтение: `plan.Reader` (порт в plan/ports.go) + `internal/planrepo/reader.go` + `internal/budget/plan_store.go`.
- Сервис: `plan.Service` (View, AddIncome, AddPayment, Delete, ExpenseCategories). В зазоре между окнами экран показывает СЛЕДУЮЩЕЕ (будущее) окно.
- Запись: `plan.Writer` + `planrepo/writer.go`; потолок суммы 1e9 единиц.
- Веб: `internal/web` (токен fail-closed, лимит неверных попыток, заголовки, Host, CSP без inline), `GET /api/plan/window`, `GET /api/plan/categories`, `POST /api/plan/income`, `POST /api/plan/payment`, `DELETE /api/plan/item/{key}`. Фронт в `internal/web/static` (ES-модули, блоки в js/blocks, реестр index.js, без innerHTML; тесты это стерегут).
- Подключение: `cmd/app/planweb.go` за `PLAN_WEB_ENABLED` (в проде true), токен `PLAN_WEB_TOKEN` (секрет GitHub), `PLAN_CHAT_IDS` (по умолчанию TELEGRAM_ALLOWED_CHATS), `PLAN_TZ` (Asia/Bangkok). Слушает 127.0.0.1:8090. Открытие: `ssh -L 8090:127.0.0.1:8090 simpleai`, затем `http://127.0.0.1:8090/#t=<токен>`.
- Безопасность (закрыто): порты 5432/8080 только на 127.0.0.1 (docker-compose, MCP_ADDR), токен Telegram-бота маскируется в логах (`internal/tools/redact.go`). Лимит памяти Postgres перенесён из ручной правки сервера в docker-compose.yml.
- Beads закрыты: 1.x, 2.0, 2.1a, 2.1b, 2.2 (selg), 2.3 в минимальном объёме (kc72, см. notes), P0 безопасность.

## Что НЕ сделано (порядок)
1. Экран: «оплачено» (платёж→факт-транзакция), «пропустить этот раз» (skipped_dates), «пришло» (поступление→факт с scheduled_for), процент резерва, ручной курс с экрана (задача 3.3c + расширение Writer; команды из C25). Повторяющиеся правила создавать/править с экрана пока нельзя (читаются из бота).
2. Воркер (2.4a отдельным деплоем, потом 2.4b shadow plan.Next против nextOccurrence ≥ суток, 2.4c удалить nextOccurrence): scheduled_for + ON CONFLICT, лимит догона ≤5, PLAN_TZ. 2.6 общая clock.Today для бота и воркера.
3. Telegram-навык «сколько можно тратить» через `plan.Service` (фаза 4, AC-7.2: одно число для бота и экрана). Старая команда «остаток по конверту» НЕ меняется (ADR-009 п.11).
4. Фаза 5 по запросу: Tailscale serve/доступ с телефона, слияние категорий, подкатегории, Excel.
5. Известные хвосты ревью: чтение всех транзакций на каждый запрос; Skipped считает и давние записи; потолок 1000 сроков повторов на все правила вместе (ErrTooMany → 500); платёж в зазоре помечается «просрочен» от даты старта будущего окна; интерфейс показывает пустую дату у платежа «в окно».
6. Владельцу: перевыпустить токен Telegram-бота через BotFather (старый остался в логах сервера).

## DRY-решение (закрыто, не переоткрывать)
`plan.Convert` и `budget.ToTHB` НЕ объединяем (int64 и только ฿/₽ против float и любых валют; подмена сдвинет суммы конвертов и golden-ответы бота). `plan.Compute` и `safetospend.computeRemaining` НЕ объединяем (разная семантика, ADR-009 п.11). Единое число бота и экрана = новый вопрос «сколько можно тратить» через plan.Service. Дубль `nextOccurrence` убираем в 2.4a–c. Перед любой новой логикой — искать готовое (budget.Store, воркер, навыки бота). Долги в план не входят (владелец не просил; понадобятся — добавить как вид платежа).

## Решения владельца (не переспрашивать)
Окно всегда 14 дней от поступления (факт или ожидаемое); нет листания окон стрелками и ориентиров по категориям; платёж без даты в расчёт не входит (по умолчанию «пока без даты»); «расход» = платёж с галочкой «уже оплачен»; повторяющиеся расходы исполняет воркер, повторяющиеся поступления — кнопка «пришло»; «пропустить этот раз» вместо привязки; остаток прошлого окна не переносится; без долгов (кредит как повтор с until), без поиска, без «остаётся» в ленте; подкатегории и слияние категорий, Excel, Tailscale/телефон — по запросу (фаза 5). Фронт без сборщика, ES-модули, один файл на блок.

## Открытые вопросы владельцу (не блокируют)
Долги (остаток, срок закрытия) — были в первом списке, в макет не вошли; перенос остатка окна; домен для HTTPS (нет → Tailscale serve); PLAN_CHAT_IDS (партнёр).
