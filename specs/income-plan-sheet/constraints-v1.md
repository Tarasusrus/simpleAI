# Constraints: Общий план прихода

Императивы: MUST / SHOULD / MUST NOT. Каждый пункт проверяем (команда или тест). Проект: Go-сервис simpleAI, PostgreSQL, goose-миграции, Telegram-бот, MCP SSE на :8080.

## Факты о коде (основа решений)
- Категории плоские: `budget_category(id, name, type, icon, sort_order)`, уникальность (name, type). Родителя нет.
- `budget_transaction` не хранит автора записи (нет колонки добавившего).
- Есть `Store.ListTransactions(filter)`, `DeleteTransaction`, правка транзакции в навыке budget; раскладка — `safetospend.PlanEnvelope` (ADR-007/008).
- HTTP в сервисе: только MCP SSE на `localhost:8080`. Порт 443 на проде занят другим сервисом (3x-ui). Публичного веб-входа у simpleAI сейчас нет.
- Следующая миграция — 00021.

## 1. Схема БД
- C1. MUST добавить `parent_id UUID NULL REFERENCES budget_category(id)` в `budget_category` (миграция 00021). Глубина дерева ровно 2 уровня; MUST проверяться CHECK-ом или кодом (подкатегория не может иметь подкатегорию).
- C2. MUST добавить `added_by TEXT NOT NULL DEFAULT ''` в `budget_transaction` (кто внёс: имя из Telegram или `web`). Существующие строки MAY остаться пустыми, экран показывает «—» (AC-3.6 для них не применяется).
- C3. MUST хранить секретный токен доступа вне БД транзакций: в конфиге/окружении (`PLAN_WEB_TOKEN`), не в репозитории. MUST NOT логировать токен.
- C4. Слияние дублей категорий MUST идти одной транзакцией БД (`BEGIN … COMMIT`) и MUST перепривязать ВСЕ ссылки на `budget_category`. Полный перечень FK (проверен по миграциям): `budget_transaction.category_id` (00007), `budget_recurring.category_id` (00011), `budget_envelope_share_category.category_id` и поле `category_name` (00017, PK `(share_id, category_name)`). Перед стартом задачи MUST быть пересчитан перечень по `information_schema` (могут быть новые таблицы).
  - C4a. Для `budget_envelope_share_category` MUST решаться конфликт ключа: если обе сливаемые категории уже стоят в одной доле, остаётся одна строка (DELETE дубля до UPDATE).
  - C4b. После слияния MUST выполняться инварианты: нет ссылок на удалённые категории; число строк с `category_id IS NULL` не выросло; `SUM(amount)` транзакций и сумма по каждому конверту/доле совпали с «до».
  - C4c. Код, матчащий категории по НАЗВАНИЮ (`IsVariableDailyExpense`, `buckets.go`), MUST быть проверен и обновлён под новые имена в той же задаче; MUST быть тест, что результаты `/envelope` и остатка до и после слияния совпадают.
- C5. Миграция MUST иметь рабочий Down (откат колонок). Слияние категорий — отдельная data-миграция, обратимость не требуется, но перед ней MUST существовать бэкап (в проде уже ежедневный).
- C6. MUST NOT менять модели LLM, таймауты, секреты бота (CLAUDE.md проекта).

## 2. Компоненты
- C7. Логика плана MUST оставаться в существующем слое (`internal/budget`, `internal/skills/safetospend`). MUST NOT дублировать раскладку в веб-слое: страница вызывает те же функции и рендерит результат.
- C8. MUST создать новый тонкий пакет веб-интерфейса `internal/web` (хэндлеры + шаблоны). Хэндлер MUST только: проверить токен → вызвать сервис → отрендерить. Бизнес-логики в хэндлере нет.
- C9. MUST ввести в `internal/web` интерфейс чтения (`PlanReader`) и интерфейс записи (`TransactionWriter`), реализуемые существующим `budget.Store`; хэндлеры зависят от интерфейсов (для моков в тестах).
- C10. Экспорт в xlsx MUST собираться из тех же данных, что и страница (одна функция сборки модели «строки таблицы»), чтобы числа не расходились. Библиотека: проверенная Go-библиотека xlsx (например excelize); MUST зафиксировать версию в go.mod.
- C11. Правка трат из бота и с экрана MUST идти через один и тот же метод Store (без второго пути записи).

## 3. API / страницы
- C12. MUST быть маршруты: `GET /plan/{token}` (страница), `GET /plan/{token}/history`, `GET /plan/{token}/tx?category=&period=` (детали, HTML-фрагмент), `GET /plan/{token}/export.xlsx`, `POST /plan/{token}/tx` (создать), `POST /plan/{token}/tx/{id}` (изменить), `POST /plan/{token}/tx/{id}/delete`.
- C13. Любой запрос с неверным токеном MUST возвращать 404 без тела, раскрывающего существование страницы. Сравнение токена MUST быть константного времени (`subtle.ConstantTimeCompare`).
- C14. Пока нет cookie-сессий, CSRF-защита не требуется (токен в пути). Если появятся cookies — MUST добавить CSRF-токен.
- C15. Страница MUST быть серверно отрисованной (Go `html/template`), JavaScript только для раскрытия строк; MUST NOT тянуть внешние CDN-скрипты. Всё экранируется шаблонизатором (защита от XSS в описаниях трат).
- C16. Ответ страницы MUST содержать ячейки лимит / потрачено / осталось / в день для каждой категории и подкатегории, итог по блоку и общий итог.

## 4. Доступ и публикация (риск)
- C17. MUST слушать веб на отдельном порту/интерфейсе, не на :8080 (MCP). Способ публикации принят в ADR-009 (docs/adr/009-plan-web-ui.md): фаза 1 — только 127.0.0.1 + SSH-туннель; публикация — отдельная фаза 2 через обратный прокси с TLS на отдельном порту/поддомене (443 занят 3x-ui). Выбор конкретного прокси зависит от одного ответа владельца: есть ли домен (открытый вопрос 9).
- C17a. Страница MUST отдавать заголовки `Referrer-Policy: no-referrer`, `Cache-Control: no-store`, `X-Robots-Tag: noindex, nofollow`.
- C17b. На неверный токен MUST действовать ограничение частоты (rate limit по IP), чтобы токен нельзя было перебирать.
- C17c. Прокси MUST не писать токен из пути в access-лог (маскирование пути `/plan/*`).
- C17d. Каждая запись/правка/удаление с экрана MUST фиксироваться в логе с `added_by=web` и идентификатором записи.
- C18. Пока TLS не настроен, веб MUST быть недоступен снаружи (слушать только `127.0.0.1`, доступ через SSH-туннель). MUST NOT открывать порт в интернет без TLS и токена.
- C19. Токен MUST быть случайным ≥ 32 байт (base64url). Ротация — замена переменной окружения и рестарт.

## 5. Стиль кода
- C20. MUST следовать существующим соглашениям пакета: структурное логирование `slog`, ошибки с `%w`, русские комментарии «зачем», как в соседнем коде.
- C21. MUST NOT использовать глобальное состояние в `internal/web`; зависимости передаются через конструктор.
- C22. MUST NOT считать деньги в хэндлере или шаблоне. Числа приходят готовыми из сервисного слоя (инвариант «числа считает Go, не LLM/шаблон»).
- C23. Суммы MUST форматироваться одним общим форматтером (как `safetospend.FmtAmount`), без второго.

- C14a. Модель доступа: токен в пути даёт полный доступ на чтение и запись (D3). Это осознанный риск владельца; смягчение — C17a–c, ротация токена (C19), TLS при публикации.

## 5a. Связь с ADR-007/008 (не дублировать расчёт)
- C31. Веб MUST брать числа из `safetospend.PlanEnvelope` / `budget.Store`; MUST NOT вводить вторую формулу раскладки.
- C32. Строка «Отложить» MUST вычитаться из `FreeAfterObligations` ДО раскладки по долям, чтобы сходимость ADR-008 §4 (сумма долей = allocated) сохранилась. Реализуется как новый вход расчёта (например, `Reserve`), а не как правка результата в веб-слое.
- C33. Строка «На долги»: MUST показываться «Нераспределено» отдельной строкой (а не подгоняться под приход); долги берутся из `budget_debt` (платёж + остаток). Если `budget_debt` пуст — подсказка, а не нули.
- C34. Доли ADR-008 привязаны к КАТЕГОРИИ верхнего уровня (родителю). У подкатегории доли нет; сумма «потрачено» родителя = своя + подкатегорий. `IsVariableDailyExpense` MUST трактовать подкатегорию по родителю.
- C35. «В день» MUST считаться в одном месте сервисного слоя одной формулой (лимит или потрачено ÷ дни периода); шаблон и xlsx её не пересчитывают.
- C36. Курс MUST браться из того же источника, что в боте (`GetExchangeRates`: ручной перекрывает автоматический).
- C37. Правка суммы с экрана MUST использовать оптимистичную блокировку по `updated_at` (новая колонка `updated_at`, `updated_by` в 00021); при конфликте — понятное сообщение, а не 500.

## 6. Стратегия тестов
- C24. Каждый AC MUST иметь тест (таблица соответствия — в verification.md). Табличные тесты, `testify`.
- C25. Сервисный слой MUST тестироваться на пустой/малой/большой сумме прихода (AC-2.2 — проверка, что доли не зависят от суммы).
- C26. Тесты хэндлеров MUST использовать `httptest` и моки `PlanReader`/`TransactionWriter`; MUST покрыть неверный токен (404) и XSS в описании.
- C27. Миграционный тест MUST прогнать слияние дублей на копии боевой структуры и сверить: сумму всех трат, привязки recurring и доли конвертов до/после (AC-4.1, AC-4.5, AC-4.6).
- C28. Тест экрана MUST проверять, что сумма деталей равна числу в ячейке (AC-1.5).
- C29. Каждый новый тест MUST быть проверен мутацией: сломать проверяемую логику и убедиться, что тест краснеет (инвариант пользователя).
- C30. MUST NOT требовать боевую БД для запуска тестов; DB-тесты пропускаются без `BOTCLIENT_DATABASE_URL_RW` или идут в docker-postgres на отдельной тестовой базе.

## 7. Решения и компромиссы (обязательно)

**D1. Формат интерфейса: веб-страница от бота + экспорт в Excel, а не Google Таблица.**
- Выбрано: страница в браузере (HTML) и кнопка xlsx.
- Отвергнуто: (а) Google Таблица как основное хранилище — нужен OAuth/сервисный аккаунт Google, двусторонняя синхронизация с базой, риск расхождения цифр, ограничения API; (б) xlsx-файл в облаке как рабочее хранилище — два человека правят копии, бот не может писать в файл надёжно.
- Почему: самый простой путь к «одному источнику правды»; общий доступ и правка одной ссылкой; никаких синхронизаций. Excel остаётся как выгрузка для тех, кто хочет.
- Цена: нужно решить публикацию веб-страницы (C17–C18) и сделать минимальный интерфейс правки.
- Пересмотр: если публикация окажется неприемлемой, запасной вариант — Google Таблица, куда бот периодически выгружает снимок (read-only вид), правка остаётся через бота.

**D2. Источник правды — база; экран не имеет копии данных.** Отвергнуто: хранить план в таблице и синхронизировать. Причина: убирает класс багов «таблица и база разошлись» (прямой ответ на открытый вопрос 1).

**D3. Доступ по секретной ссылке без логинов.** Отвергнуто: логин/пароль и роли (владелец явно не хочет). Цена: у любого, кто получил ссылку, полный доступ; смягчение — длинный токен, ротация, TLS обязателен для публикации.

**D4. Подкатегории через `parent_id`, глубина 2.** Отвергнуто: произвольная вложенность (избыточно), отдельная таблица подкатегорий (две сущности вместо одной). Простейшее, что даёт «категория → кофе».

**D5. Автор записи в отдельной колонке, не отдельная таблица аудита.** Отвергнуто: полный журнал изменений. Достаточно «кто внёс»; история правок вне области.

**D6. Серверный рендер, без SPA.** Отвергнуто: React/SPA — лишняя сборка, зависимости, поверхность атаки. Раскрытие строк делает маленький встроенный скрипт.

**D7. Слияние дублей категорий — отдельной data-миграцией с проверкой суммы.** Отвергнуто: ручная правка в проде. Причина: деньги не должны потеряться (AC-4.1).
