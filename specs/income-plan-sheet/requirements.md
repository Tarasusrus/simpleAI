# Requirements: План окна (v8.3)

Основа: утверждённый макет mockup.html, принципы владельца, три цикла ревью (QA и время, эксплуатация и безопасность, продукт против заметок). Предыдущие версии: *-v1, *-v8.1. **При расхождении макета и этой спеки побеждает спека**; макет будет приведён к ней вместе с фронтом (task-3.4b). Отличия макета от спеки: колонки категорий (макет: «Сентябрь / Обычно», спека: «Прошлое окно / Сейчас»); галочка «ориентир» и стрелки окон убраны; колонки «остаётся» в ленте нет; кнопки «пришло» у повторяющихся доходов в макете есть — в спеке есть (R3b), но без сдвига дат на стороне экрана.

## Принципы владельца
SOLID, DRY, KISS, YAGNI. Одна логика, два интерфейса (Telegram и экран) на одних данных. Изменения частые и простые: блок экрана добавляется отдельным файлом. Вся логика расчёта в Go (BFF), фронт рисует готовое.

## Время и окна
- R1. **Окно** — 14 календарных дней `[start, start+13]` включительно. `start` — дата поступления (пришедшего или ожидаемого). Поступления окна складываются; поступление позже конца окна открывает новое. Окна вычисляются, не хранятся. Без поступлений окон нет: экран показывает «Внесите поступление».
- R1a. **Сегодня** — календарная дата без времени в зоне `PLAN_TZ` (по умолчанию `Asia/Bangkok`). Экран, бот и воркер берут её из одного места.
- R1b. **Состояния времени** (таблица в domain-types.md): `current` (daysLeft = `end − today + 1`, сегодня входит), `upcoming` (14), `between` и `ended` (0; «Окно закончилось, следующее начнётся DD.MM»; остаток прошлого окна НЕ переносится и не показывается (YAGNI)), `none`. «Ожидаемое окно» (открыто ожидаемым поступлением) и положение во времени — независимые признаки.

## Модель события
- R2. Событие денег: направление (поступление / платёж) × состояние (запланировано / факт). Платёж «уже оплачен» = факт расхода, отдельного «расхода» нет.
- R2a. Валюты THB и RUB (и у поступления тоже). Любая другая — отказ 400 «валюта не поддерживается».
- R2b. Оплата частями вне области: обход — правка суммы пункта и новый оплаченный платёж.
- R3. **Повтор**: «каждые N [дней / недель / месяцев / лет]», N ≥ 1, `until` включительно. n-й срок = якорь + n·N с клампингом на последний день короткого месяца (не цепочка от предыдущего срока: 31.01 → 28.02 → 31.03).
- R3a. **Повторяющийся расход**: факт создаёт воркер в день срока; идемпотентность по `(recurring_id, scheduled_for)`. Воркер не создаёт сроки раньше даты создания правила; догоняет пропущенные при простое не более 5 за тик на правило, одно сводное сообщение; срок старше 62 дней факт не создаёт (Warn и сообщение владельцу). Действие **«пропустить этот раз»** добавляет срок в исключения правила (якорь не двигается); нужно, если оплатил сам или платёж не нужен.
- R3b. **Повторяющееся поступление**: воркер факт НЕ создаёт; событие остаётся ожидаемым, пока владелец не подтвердит «пришло» (сумма и дата предзаполнены, правятся). Подтверждение создаёт факт с `scheduled_for`.
- R3c. Сумма повтора — оценка. Правка суммы правила действует с ближайшего неисполненного срока, прошлые факты не меняются; правка факта правило не меняет.
- R4. **Платёж без даты** хранит выбранное окно как дату `window_start` (резолвится при действии «в это окно» / «в следующее»); без выбора лежит в «Без даты» и в расчёт не входит. Принадлежность: платёж с `window_start` относится к первому окну, у которого `end ≥ window_start`. Нет такого окна — платёж показывается в «Без даты» с пометкой «окно ещё не создано»; если окно уже прошло, а платёж не оплачен — «окно прошло» (напоминание не теряется, в расчёт не входит).
- R4a. Под главным числом: «ещё N без даты на M ₽, не вычтены».
- R5. **Платёж без суммы** допустим (напоминание), в расчёт не входит; «N без суммы, не вычтены». Поступление без суммы, нулевая и отрицательная сумма — отказ 400.
- R5a. **Просроченный разовый платёж** (повторяющиеся не бывают просроченными: факт создаёт воркер) (дата раньше сегодня, не оплачен): входит в расчёт текущего окна независимо от даты, стоит наверху ленты с пометкой «просрочен N дн.», есть «оплачено» и «перенести».
- R5b. «Оплачено» открывает строку подтверждения (сумма, валюта, дата предзаполнены из плана): факт создаётся с введёнными значениями; платёж закрывается (`settled`).
- R5c. Если расход, внесённый ботом или формой, по названию совпадает с открытым плановым пунктом, система спрашивает «закрыть пункт этой оплатой?» (иначе пункт будет вычтен второй раз).

## Главный экран
- R6. Две кнопки добавления: «＋ Поступление» и «＋ Платёж» (галочка «уже оплачен» делает платёж фактом), плюс курс бата и переключатель ₽/฿.
- R7. Строка окна: даты, «пришло A, ожидается B», осталось дней (только у текущего окна).
- R8. **Главные числа** (все считает BFF): `canSpend = (пришедшие + ожидаемые поступления окна) − платежи окна − фактические расходы окна − резерв`. `perDay = canSpend ÷ daysLeft`; при `daysLeft = 0` или `canSpend < 0` — «—» (не 0 и не бесконечность). «Платежи и расходы» = `payments + spent` (непересекающиеся). Факт, порождённый платежом, считается один раз.
- R8a. **Резерв**: «откладывать N% от поступлений окна», N — настройка плана (по умолчанию 0), считается от суммы поступлений окна (пришедших и ожидаемых), строка видна, если N > 0.
- R9. **Лента** «Ближайшие платежи»: события окна по дате; при равенстве — поступления, затем платежи, затем по названию. Затем «в это окно» без точной даты. Просроченные — сверху. Показываются 6, остальное под «Показать все N». Колонки «остаётся» нет (YAGNI).
- R10. **Следующее окно** — одна свёрнутая строка «N платежей, сумма Y»; если следующего окна нет — блок скрыт. Дальние платежи — свёрнутые группы по месяцам, горизонт 6 месяцев.
- R11. «Без даты · N · не входят в расчёт» — свёрнутый список с действиями «в это окно» / «в следующее».
- R12. **Как обычно тратишь**: по категориям «Прошлое окно» (фактические траты предыдущего окна) и «Сейчас» (в этом окне), строка «Без категории»; у категории — последние траты. Ориентиров и лимитов нет.
- R13. Курс ₽/฿ из `GetExchangeRates` (ручной перекрывает автоматический); BFF отдаёт числа уже в выбранной валюте показа.

## Вкладки и ввод
- R14. «Платежи»: «＋ Добавить платёж»; списки: повторяющиеся / разовые с датой / без даты / потрачено (факт) / поступления; у каждой записи «изменить» и «удалить». Поиска нет (YAGNI).
- R15. «История»: категории × месяцы, клик по месяцу показывает транзакции. Транзакции видны только здесь и в деталях категории.
- R16. **Telegram** — те же действия через тот же сервис. Список пунктов одним сообщением: бот показывает разобранный список и ждёт «да». «50.000» → 50 000; «98 тысяч» → 98 000; без валюты — `PLAN_DEFAULT_CURRENCY` (RUB), бот подтверждает валюту. Неоднозначное имя — переспрашивает со списком.
- R17. Доступ по секретному токену, без ролей; фаза 1 — только 127.0.0.1 + SSH-туннель.

## Вне области (YAGNI), решения по умолчанию
Долги (остаток, срок закрытия): кредит виден как повторяющийся платёж с `until`. Оплата частями. Предупреждение о дубле «пункт против правила». Листание окон и ориентиры. Роли, графики. Excel, доступ партнёру/телефону, подкатегории и слияние категорий — по запросу владельца (фаза 5).
