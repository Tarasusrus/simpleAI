# Requirements: План окна (утверждённый дизайн v8)

Источник: proposal.md + макет [mockup.html](mockup.html), утверждённый владельцем 2026-10-16 («в общем и целом утверждаю»). Прежняя версия сохранена как requirements-v1.md. Макет — источник истины по поведению экрана; здесь он переведён в проверяемые требования.

## Принципы (от владельца, обязательны для реализации)
- **SOLID, DRY, KISS, YAGNI.** Изменения будут частыми — каждое должно быть маленьким и локальным.
- **Одна логика, два интерфейса.** Telegram доставляет данные, экран их показывает. Вся логика экрана живёт в Go-проекте (Backend for Frontend, BFF); фронт только рисует готовые числа.
- **Модульность.** Блок экрана добавляется или меняется без правки соседних блоков.

## Модель
- R1. **Окно** — всегда 14 дней. Начинается с даты поступления (пришедшего или ожидаемого). Поступление внутри окна добавляется к его сумме; поступление после конца окна открывает новое. Окна не хранятся, а вычисляются из поступлений.
- R2. **Событие денег** имеет направление (поступление / платёж) и состояние (запланировано / факт). Платёж «уже оплачен» = фактический расход. Отдельного понятия «расход» нет.
- R3. **Повтор** задаётся правилом «каждые N [дней / недель / месяцев / лет]» и необязательной датой окончания. Работает и для платежей, и для поступлений. Без правила событие разовое. У повторяющегося события факт создаёт воркер в день срабатывания (одна логика повтора на весь проект); «пришло» / «оплачено» есть только у разовых.
- R4. **Платёж без даты** лежит в списке «Без даты» и в расчёт НЕ входит. Владелец одним действием переносит его «в это окно», «в следующее» или ставит дату.
- R5. **Платёж без суммы** допустим (напоминание). В расчёт не входит; экран явно показывает «N без суммы, не вычтены».

## Экран «Окно» (BFF отдаёт готовую модель, см. constraints)
- R6. Вверху три кнопки добавления: «＋ Поступление», «＋ Платёж» (две; расход — это платёж с отметкой «уже оплачен»), и курс бата с переключателем ₽/฿.
- R7. Строка окна: даты окна, сумма поступлений, осталось дней (только у текущего окна).
- R8. Три главных числа: «Можно тратить до конца окна», «В день» (÷ оставшиеся дни), «Платежи и расходы в окне». Формула: поступления окна − платежи окна − плановые разовые с суммой − фактические расходы − отложенное.
- R9. «Ближайшие платежи» — события окна по датам, поступления тоже, у каждого платежа «остаётся». Показываются первые 6, остальное под «Показать все N».
- R10. Следующее окно — одна свёрнутая строка: «Следующее окно: придёт X, платежи Y, останется Z». Раскрытие показывает платежи. Дальние платежи собраны по месяцам, свёрнуты.
- R11. «Без даты · N · не входят в расчёт» — свёрнутый список с действиями «в это окно» / «в следующее».
- R12. «Как обычно тратишь» — по категориям два числа: **«Прошлое окно»** (фактические траты предыдущего 14-дневного окна) и **«Сейчас»** (в этом окне). У категории — последние траты (подкатегории позже, см. A8). Ориентиров и лимитов на экране нет (решение владельца: ориентир убран).
- R13. Курс ₽/฿ редактируется; все суммы пересчитываются на стороне BFF; переключатель валюты показа.

## Экран «Платежи» и «История»
- R14. «Платежи»: кнопка «＋ Добавить платёж», поиск, списки: повторяющиеся, разовые с датой, без даты, потрачено (факт), поступления. Любую запись можно изменить или удалить (исправление ошибок).
- R15. «История»: категории × месяцы, клик по месяцу показывает траты. Транзакции видны только здесь и в деталях категории (не шумят на главном экране).

## Доставка
- R16. Telegram: те же действия (добавить платёж / поступление, отметить оплаченным, «сколько можно тратить») через тот же сервис. Бот и экран видят одни данные.
- R17. Доступ по секретной ссылке, без ролей. Публикация по HTTPS отдельной фазой (нужен домен, пока нет): до этого только 127.0.0.1 + SSH-туннель. Скачивание Excel — из той же модели (фаза позже).

## Вне области сейчас (YAGNI)
Листание окон стрелками (отклонено владельцем; вместо него свёрнутая карточка «Следующее окно»), ориентиры по категориям, роли, графики, двусторонняя синхронизация, дальние прогнозы.

## Допущения (владелец может изменить)
- A1. Сегодняшнюю дату берёт сервер (календарь). В макете поле «Сегодня» — только для проверки.
- A2. «Прошлое окно» считается по реальной истории поступлений в базе; если истории поступлений нет — колонка пустая с подсказкой.
- A3. Курс по умолчанию — из бота (ручной перекрывает автоматический).
- A4. Остаток прошлого окна НЕ переносится в следующее (вопрос задан владельцу, ответа нет); решение отложено, закладывается точка расширения.
- A5. Область данных — чаты из `PLAN_CHAT_IDS` (владелец и, при желании, партнёр). Транзакции общие, как сейчас в боте.
- A6. При одновременной правке одной записи побеждает последнее сохранение; потеря чужой правки принимается.
- A7. Для повторяющихся событий факт создаёт существующий воркер в день срабатывания; кнопки «пришло»/«оплачено» есть только у разовых плановых записей.
- A8. Подкатегории (раскрытие «Еда → продукты / кафе») появятся после слияния дублей категорий (фаза 5, нужен `parent_id`); до этого строки категорий плоские.
