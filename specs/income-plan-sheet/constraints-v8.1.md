# Constraints: План окна (v8, BFF-архитектура)

MUST / SHOULD / MUST NOT, каждый пункт проверяем. Прежняя версия: constraints-v1.md. Решения: ADR-009 (docs/adr/009-plan-web-ui.md). Принципы владельца: SOLID, DRY, KISS, YAGNI, модульность.

## 0. Что переиспользуем (DRY)
`budget.Store` (транзакции, категории, курсы, `GetExchangeRates`), `budget_recurring` (уже умеет `type` expense/income), `budget_planned_expense`, `safetospend.FmtAmount/FmtRate`, `budget.ToTHB`, `internal/rates`. Конверты (ADR-007/008) и их лимиты по категориям в новом экране НЕ используются: ориентиры убраны владельцем.

## 1. Слои и зависимости (SOLID)
Зависимости идут только вниз: `web` и `telegram` → `plan.Service` → `plan` (домен) ← `planrepo` (адаптер к `budget.Store`).

- C1. **`internal/plan` — чистый домен.** MUST NOT импортировать pgx, net/http, telegram, форматирование строк, `budget.Store`. Только типы и функции от входных данных (время приходит параметром `now`). Содержит: типы `Event`, `Rule`, `Window`, `View`; `Occurrences(rule, from, to)`; `BuildWindows(incomes)`; `Compute(in) View`.
- C2. **Порты (Dependency Inversion).** `plan` объявляет маленькие интерфейсы: `Reader` (события, расходы, категории, курс) и `Writer` (команды). MUST быть раздельными (Interface Segregation): веб-чтению не нужны методы записи. Реализует адаптер `internal/planrepo` поверх `budget.Store`.
- C3. **`plan.Service`** — оркестрация: загрузить данные через `Reader`, вызвать `Compute`, выполнить команды через `Writer`. MUST быть единственной точкой входа для веба и Telegram (одна логика, два интерфейса).
- C4. **`internal/web` — тонкий BFF.** Хэндлер: проверить токен → разобрать запрос → вызвать `plan.Service` → отдать JSON. MUST NOT содержать расчётов, ветвлений по бизнес-правилам, форматирования денег.
- C5. **Telegram** — тонкий навык `plan` (или действия существующего budget-навыка), вызывающий `plan.Service`. MUST NOT считать «можно тратить» своей формулой (AC-7.2).
- C6. Новые зависимости между пакетами MUST быть проверены тестом архитектуры (`go list`/импорты): `plan` не импортирует ничего из проекта, кроме stdlib.

## 2. Контракт BFF (граница с фронтом)
- C7. `GET /api/plan/{token}/window?offset=0&cur=RUB` возвращает один JSON `WindowView` (версия поля `v`): `window{start,end,planned,daysLeft}`, `kpi{canSpend,perDay,payments,spent,unpriced}`, `timeline[]`, `next{count,sum,items[]}`, `later[]` по месяцам, `inbox[]`, `categories[]`. Все деньги уже в запрошенной валюте, округлены, с признаком недостачи. Фронт MUST NOT пересчитывать деньги.
- C8. Команды — JSON `POST`: `/api/plan/{token}/income`, `/payment`, `/payment/{id}/paid`, `/payment/{id}`(PUT/DELETE), `/income/{id}`, `/rate`. Каждая возвращает обновлённый `WindowView`.
- C9. Контракт описан в `specs/income-plan-sheet/contract.md`. Тест контракта — golden на СТРУКТУРУ (набор ключей и типов) плюс отдельные тесты значений по блокам, чтобы частая правка одного блока не ломала весь golden. Изменение поля, ломающее потребителя, MUST менять версию `v`.
- C10. Ошибки: 400 с понятным текстом на русском, 404 для чужого токена/id, 500 без деталей наружу (в логе — подробности без токена).

## 3. Фронт (простые изменения)
- C11. Фронт — статика, встроенная в бинарь (`embed`), без сборщика и внешних CDN: ES-модули, по одному файлу на блок (`kpi.js`, `timeline.js`, `categories.js`, `inbox.js`, `forms.js`, `history.js`) + `api.js` + реестр блоков. Добавить или убрать блок = один файл + одна строка в реестре.
- C12. Модуль блока — чистая функция `render(viewPart) → html`. MUST NOT читать чужие части состояния или DOM других блоков.
- C13. Любой пользовательский текст MUST экранироваться (защита от XSS). Деньги форматируются одним форматтером из `api.js` по готовым числам.
- C14. Макет `mockup.html` остаётся эталоном внешнего вида; фронт повторяет его вёрстку, но не расчёт.

## 3a. Область данных и изоляция (ADR-004)
Факты из кода: `budget_transaction` НЕ имеет `chat_id` (общая для всех, как сегодня в боте); `budget_recurring`, `budget_planned_expense`, `budget_reminder`, конверты привязаны к `chat_id`.
- C32. Область плана задаётся конфигом `PLAN_CHAT_IDS` (список; по умолчанию — владелец из `TELEGRAM_ALLOWED_CHATS`). Токен веба открывает ровно эту область, не «всё».
- C33. `Reader` и `Writer` принимают область (`Scope{ChatIDs}`) параметром. Чтение chat-привязанных таблиц MUST фильтровать по ней; запись MUST ставить `chat_id` из области (по умолчанию первый). Транзакции остаются общими (как в боте); границу «кто внёс» даёт `added_by`.
- C34. Запись другого чата вне области MUST быть невидима и не изменяема через веб (AC-8.4).

## 3b. Источники событий денег (одно правило, без двойного учёта)
- C35. **Фактические поступления** = `budget_transaction` с `type='income'`. **Фактические расходы** = `type='expense'`.
- C36. **Ожидаемые поступления/платежи** = (а) `budget_recurring` (направление из `type`), (б) разовые записи `budget_planned_expense` (`direction`).
- C37. **Приоритет факт против плана.** Событие правила повтора, для которого уже есть транзакция с `recurring_id` в этот срок, показывается ТОЛЬКО как факт (использовать существующий `GetExecutedRecurringIDs`, не писать второй). Разовая запись `settled=true` не показывается как план.
- C38. Тестовые поступления (например три по 10 ₽ 8 мая) MUST не искажать «Прошлое окно»: чистка данных в фазе 5 (владелец решает по каждой записи); до тех пор окно, содержащее только поступления меньше `PLAN_MIN_INCOME` (по умолчанию 100 ₽), якорем не считается.

## 4. Данные (миграции, добавочные)
- C15. Миграция 00021 (отдельно от других, номер подтвердить после слияния PR #63, где 00020).
  - `budget_planned_expense`: добавить `direction text NOT NULL DEFAULT 'expense' CHECK (income|expense)`, `category_id` (nullable), `window_hint` (cur|next|NULL); `amount` стать nullable. Поле `settled` ОСТАЁТСЯ источником правды (поле `status` НЕ вводить — YAGNI). `due_date` уже nullable.
  - **Потребители не ломаются в той же задаче.** `Store.PlannedExpensesTHB` и `Store.ListPlannedExpenses` MUST получить `AND direction='expense' AND amount IS NOT NULL`; других читателей нет (проверено поиском: `safetospend/remaining.go`, `safetospend/skill.go`, `budget/limits.go`, `budget/envelope.go`). Тест на копии структуры: ответы `/envelope` и «остаток» до и после 00021 совпадают, пункты без суммы и поступления в «свободно» бота не попадают.
  - `budget_recurring`: добавить `interval_n int`, `interval_unit text`, `until date`. Старые `recurrence_type` и `day_of_month` НЕ удаляются и остаются заполненными (Down и совместимость). Детерминированный бэкфилл: monthly → (1, мес), weekly → (1, нед), daily → (1, дн). Правило «конец месяца»: `day_of_month` 29–31 в коротком месяце — последний день месяца (как сейчас в `nextOccurrence`).
  - `budget_transaction.added_by text NOT NULL DEFAULT ''` (кто внёс); старые строки пустые.
  - Рабочий Down; тест миграции на копии боевой структуры.
- C16. (слито в C15) `added_by` — имя Telegram или `web`; к области (C33) отношения не имеет.
- C17. Окна, KPI и «прошлое окно» MUST вычисляться, а не храниться. Таблицы окон нет.
- C18. Миграции с рабочим Down; данные существующих платежей не теряются; тест миграции на копии структуры.
- C19. Слияние дублей категорий — отдельная фаза и отдельная data-миграция, одной транзакцией, с перепривязкой `budget_transaction`, `budget_recurring`, `budget_envelope_share_category` (подробно constraints-v1.md C4–C4c).

## 4a. Один движок повторов
Факт из кода: `internal/notify/recurring_worker.go` каждую минуту сам создаёт транзакцию на день срабатывания и сдвигает `next_date` (`CreateRecurringTransaction`), функция `nextOccurrence`.
- C39. Вычисление «следующая дата правила» MUST существовать в ОДНОМ месте: `plan.Next(rule, after)`. Воркер MUST перейти на неё (тот же код, что для окон на экране); старая `nextOccurrence` удаляется.
- C40. Для повторяющихся платежей и поступлений кнопки «оплачено» / «пришло» НЕТ: факт создаёт воркер в день срабатывания. Владелец исправляет созданную транзакцию правкой. Действие «оплачено» / «пришло» существует только для разовых плановых записей (ставит `settled=true` и создаёт транзакцию в одной БД-транзакции).
- C41. Тест: одно срабатывание правила (день, воркер и ручная правка вместе) даёт ровно одну транзакцию (идемпотентность по `recurring_id` + дате).

## 4b. Параллельные правки и команды
- C42. Каждая команда BFF MUST выполняться одной транзакцией БД (всё или ничего).
- C43. Политика параллельных правок: «последний сохраняет»; потеря чужой правки осознанно принимается (один владелец, редкие конфликты), оптимистичная блокировка из v1 не вводится (YAGNI). Фиксируется как допущение A6 в requirements.
- C44. Ручной курс: команда `rate` пишет через существующий `SetManualRate`, читает `GetExchangeRates` (один источник; зависит от слияния PR #63).

## 5. Безопасность
- C20. Фаза 1: слушать только `127.0.0.1`, порт отдельный от MCP :8080; доступ с компьютера через SSH-туннель. Доступ с телефона и партнёру — фаза 5.1 БЕЗ домена: рекомендованный путь — Tailscale (`tailscale serve` даёт HTTPS внутри закрытой сети); альтернатива — домен и прокси с TLS. Выбор фиксируется ADR-009 после ответа владельца. Порт 443 не трогать (занят 3x-ui).
- C21. Токен ≥ 32 байт из окружения `PLAN_WEB_TOKEN`, сравнение за константное время, 404 без тела, rate limit на неверный токен, заголовки `Referrer-Policy: no-referrer`, `Cache-Control: no-store`, `X-Robots-Tag: noindex`, токен не пишется в логи.
- C22. Записи с экрана фиксируются в логе с `added_by=web` и id записи.

## 6. Тесты (каждый AC → тест)
- C23. Домен `plan` MUST покрываться табличными тестами без базы: окна, повторы (дни/недели/месяцы/годы, конец месяца, until), без даты / без суммы, оплачено ≠ двойной учёт, отрицательный остаток, валюта.
- C24. Есть golden-фикстура из макета: вход «зарплата 98 000, платежи, расходы 5 758» → выход «можно тратить 45 542» (AC-4.1).
- C25. Хэндлеры — `httptest` с моком `plan.Service`-интерфейса; токен, rate limit, XSS в названии, ответы JSON по контракту.
- C26. DB-тесты пропускаются без `BOTCLIENT_DATABASE_URL_RW`; идут на отдельной тестовой базе, не на боевой.
- C27. Каждый новый тест MUST пройти проверку мутацией (сломать логику — тест краснеет). Особо: подмена имени в модуле не действует на значение по умолчанию в сигнатуре (инвариант владельца) — проверять аргумент вызова, а не «тест не упал».
- C28. Поведение бота до и после изменений (`/envelope`, остаток) MUST совпадать (AC-8.3 v1).

## 7. Стиль
- C29. Следовать соглашениям проекта: `slog`, ошибки `%w`, русские комментарии «зачем», `gofmt`, golangci-lint чистый.
- C30. MUST NOT: глобальное состояние, `init()` с побочными эффектами, дублирование формул, форматирование денег вне общего форматтера, LLM-вызовы в расчёте («числа считает Go»).
- C31. MUST NOT менять LLM-модели, таймауты и секреты (CLAUDE.md проекта).

## 8. Решения и компромиссы
**D1. Окно вычисляется, не хранится.** Отвергнуто: таблица окон/конвертов (как ADR-007). Причина: нет рассинхронизации, правки поступлений и платежей автоматически перестраивают окна; цена — расчёт на каждый запрос (дёшево, сотни записей).
**D2. Чистый домен + порты.** Отвергнуто: считать в SQL или в хэндлере. Причина: одна формула для экрана и бота, тестируется без базы, меняется в одном месте.
**D3. Фронт без сборщика, ES-модули + embed.** Отвергнуто: React/SPA и шаблоны на сервере. Причина: простые частые правки, нет зависимостей и поверхности атаки; BFF отдаёт готовую модель, фронту нечего считать.
**D4. Один тип «событие денег» (направление × состояние) вместо трёх сущностей.** Отвергнуто: «расход», «платёж», «плановый доход» отдельно. Причина: владелец показал, что различие только во времени; меньше кода и форм.
**D5. Расширить существующие таблицы, а не заводить новые.** Отвергнуто: новая `budget_events`. Причина: DRY, бот уже пишет в них; цена — миграция данных правил повтора.
**D6. Листание окон стрелками и ориентиры по категориям не делаем.** Отвергнуто владельцем: неудобно на телефоне, непонятно. Вместо этого свёрнутая карточка «Следующее окно» и колонка «Прошлое окно».
**D7. Остаток окна не переносится** (A4): отложено до ответа владельца; точка расширения — поле `carry` в `Compute`-входе, по умолчанию 0.
