# ADR-016: Бот читает и пишет лимиты через plan.Service (единое ядро лимитов)

- **Статус:** Proposed (правки по ревью architect внесены; решения владельца записаны ниже)
- **Дата:** 2026-10-23
- **Контекст:** требование владельца: лимиты живут в ядре и одинаковы для всех интерфейсов; сейчас расходятся.
- **Задача:** simpleAI-k12g
- **Заменяет:** ADR-011 §5 («лимиты плана и конверты ADR-008 независимы») и ADR-009 §11 («не используем
  конверты и лимиты по категориям»). При приёмке этого ADR статусы этих пунктов правятся.
- **Дополняет:** ADR-009 §3 («расчёт „можно тратить“ существует в одном экземпляре» — для экрана и
  Telegram; для бота не выполнено).
- **Связи:** ADR-008, ADR-011, ADR-013 (§5 переносит «Еду» в обеих моделях), ADR-015 (§9, новые функции
  плана), ADR-017 (судьба модели конвертов, отдельное решение).

Разделено на два ADR: этот (чтение и запись бота через plan, данные не мигрируются, всё обратимо) и ADR-017
(что делать с таблицами конвертов, необратимая часть).

## Контекст

Факты по коду (2026-10-23):

1. Веб читает и пишет лимиты через `plan.Service` и `plan_category_limit` (ADR-011): лимит на окно, повтор,
   остаток `max(лимит − потрачено − плановые, 0)`, вычитается из «Свободно» (`LimitHold`), отдельно `Over`.
2. Бот считает иначе: доли конверта `budget_envelope_share` (ADR-008), лимит доли `Allocated + CarriedIn`,
   остаток `computeShareRemaining` без нижней границы (может быть отрицательным), только переменные
   потребительские категории (`IsVariableDailyExpense`), fallback-доля «прочее». Правка словами
   `set_share_limit` пишет `budget_envelope_limit_override`; предупреждение при трате — `ShareRemainingFor`.
   Дневной лимит бота — `DailyLimit` (`safetospend/allocate.go`, `format.go`) — отдельно от `PerDay` экрана.
3. Ни `skills`, ни `agent`, ни `bot` не импортируют `internal/plan`; импортируют `web`, `planrepo`, `cmd/app`.
4. `plan.Service` собирается с **фиксированным `Scope`** из `PLAN_CHAT_IDS` один на процесс
   (`cmd/app/planweb.go`), бот — многочатовый (`ChatIDKey` в ctx). Весь план за `PLAN_WEB_ENABLED`.
5. В `plan.View` **лимитов нет, если нет прихода в окне** (ADR-011 §3), конверт же существует отдельно от окна.
6. Лимит плана привязан к одной категории по имени; доля бота — набор категорий + fallback.
7. Учёт трат: у `budget_transaction` нет `chat_id` (ADR-008), область чатов у плана — `Scope.ChatIDs`.

## Решение

### 1. Ядро — `internal/plan`
Единственная реализация лимитов: модель, остаток, влияние на «Свободно», дневной лимит. Бот, пуш и веб читают и
пишут лимиты **только** через `plan.Service`. Второй расчёт остатка категории или «можно тратить» запрещён.
Домен остаётся чистым (`arch_test.go`): всё новое для бота — чистые функции, «сегодня» параметром, форматирование
в `skills`.

### 2. Chat-scope
`Service.scope` зашит при создании. Решение: **`Scope` передаётся параметром запроса** для вызовов бота
(второй конструктор `ForChat`/метод с `Scope` вместо фабрики на чат; конкретная форма выбирается при реализации,
публичный API plan меняется явно). Чат бота вне `PLAN_CHAT_IDS` или без прихода в окне **обслуживается старым
путём** (поведение как до ADR), ответ не «лимитов нет». Разница между `Scope` плана и чатом бота фиксируется
в коде и тестом (ограничение ADR-008 про `chat_id` у транзакций сохраняется).

### 3. Валюта
Бот считает в THB, `View` отдаёт валюту показа. Бот запрашивает `View` в валюте чата (или THB) и **называет
валюту в ответе**; тест паритета — в одной валюте. «Хватит 15000» без валюты: прежний дефолт RUB (как
`setShareLimit`) → `NewLimit` в этой валюте; лимит плана хранит валюту и конвертируется по курсу, значит THB-расчёт
бота перестаёт быть источником истины.

### 4. Период
Лимит плана действует на окно плана (14 дней от поступления), конверт — на свой период. Решение (вопрос
владельцу ниже): **главное окно плана**. Ответы бота «до N числа» берут конец окна плана. Два случая явно:
конверт активен, окна нет → старый путь; окно есть, конверта нет → ответ из плана.

### 5. Набор категорий и формула
Побеждает формула плана: лимит можно поставить на любую расходную категорию, остаток `max(…, 0)` и `Over`
отдельно, recurring (`RuleID`) не едят лимит, неоплаченные плановые платежи едят. Это видимое изменение
для бота (отрицательный остаток превращается в «пробито на N» через `Over`); показывается в сеансе сравнения
до включения (§8).

### 6. Что бот делает через plan
- «Сколько осталось на еду», предупреждение при трате (`add_expense`), «на день»/«Свободно» — из `plan.View`/`LimitView`
  (`PerDay`, `CanSpend`). Если у категории нет лимита — предупреждения нет (раньше падало в «прочее»).
- `set_share_limit` («на еду хватит 15000») → `plan.Service` (добавить/изменить лимит категории), новое имя
  действия остаётся для совместимости с golden-set; `clear` — удаление. Запись в
  `budget_envelope_limit_override` прекращается на этапе записи (§8, шаг 3).
- Функции ADR-015 (блок «Не запланировано», «Запланировать», трата внутри категории) бот получает из ядра без
  второй реализации.

### 7. Инварианты и тесты
- Один тип остатка: `plan.LimitView.Left/Over`. Бот форматирует, не считает.
- **Тест паритета** на общей фикстуре: несколько категорий, recurring-факт, плановый платёж без суммы, RUB и
  THB, граница окна. Сравниваются **числа до форматирования** (`LimitView.Left/Over`, `View.PerDay`, `CanSpend`
  и то, что бот передал форматировщику), не строки. Мутации: убрать вызов `plan` в боте и подставить старый
  расчёт — красный; убрать фильтр `RuleID` в plan — красный тест plan.
- **Архитектурный тест:** запрещены вызовы методов `budget.Store` старого пути (`ResolveShare`, `SetOverride`,
  `ReplaceShares`, чтение `budget_envelope_share*`) из `skills/*` и `bot`; проверка по символам и импортам, не
  по тексту SQL. Белый список на переходный период (пока старый путь жив за флагом), сужается каждым шагом.
- Golden-set бота `r043`–`r047` обновляется до кода; правка роутинга — в `ROUTING RULES`
  (`internal/agent/router.go`), не только в Manifest (ADR-008). Слово «конверт» в ответах бота
  пересматривается (ADR-011 §1).

### 8. Выкатка и откат
1. **Флаг бота** `BOT_LIMITS_FROM_PLAN`, независимый от `PLAN_WEB_ENABLED` (иначе включение веба молча переключает бота).
2. **Shadow-режим:** бот считает по старому пути и параллельно по plan, расхождение пишется в лог (`chat_id`,
   категория, оба числа), пользователю не показывается. Даёт реальный паритет на проде.
3. **Чтение за флагом** → сеанс «до/после» на реальных данных владельца → включение. Откат: флаг.
4. **Запись `set_share_limit` в plan:** данные расходятся (правки только в plan). Либо **dual-write** на время
   этапа (пишем и в plan, и в override), либо явное «откат только вперёд». Выбор — при реализации шага, фиксируется
   в задаче.
5. Удаление старого пути — только после периода без регрессий, отдельным релизом (ADR-017).

## Решения владельца (2026-10-23)
1. Главное окно — **окно плана** (не период конверта).
2. «Свободно» и «на день» в боте и на экране — **одно число**.
3. Допуск расхождения в сеансе «до/после» — решает владелец по цифрам dry-run/shadow, порог заранее не задан.
4. Конверты не используются и устаревают (ADR-017). Область чатов бота — как у веба (`PLAN_CHAT_IDS`),
   пока владелец не скажет иное; формат ответа: остаток плана с `Over` («пробито на N»), отрицательный остаток
   из старой модели не воспроизводится.

## Последствия
+ Один расчёт, одни числа в боте, на экране и в пуше; новые функции пишутся один раз.
+ Обратимо: флаг, shadow, старый путь жив.
− Бот в проде: числа в ответах изменятся (формула плана, период, набор категорий), нужен сеанс сравнения.
− Меняется публичный API `plan` (Scope на запрос).
− Пока ADR-017 не принят, две модели хранения живут параллельно.

## Декомпозиция (после ответов владельца и вердикта architect)
1. `plan`: `Scope` на запрос; порт `LimitsReader` для бота в `skills`.
2. Бот читает остаток и `PerDay` из plan за флагом + shadow-лог расхождений.
3. Тест паритета бот ↔ веб (числа до форматирования, мутации) + архитектурный тест с белым списком.
4. Предупреждение при трате (`add_expense`) из plan (поведение без лимита категории — отсутствие предупреждения).
5. `set_share_limit`/clear → `plan.Service` (dual-write или откат вперёд), golden-set и `ROUTING RULES`.
6. Правка статусов: ADR-009 §11, ADR-011 §5, ADR-013 §5, ADR-015 §9.
