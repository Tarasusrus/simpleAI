# ADR-008: Категорийные конверты — доли прихода (envelope shares)

- **Статус:** Accepted
- **Дата:** 2026-08-23
- **Контекст эпика:** simpleAI-faeq
- **Заменяет / дополняет:** ADR-007 (safe-to-spend, живой конверт). Инварианты ADR-007 §4 (недвойной учёт) действуют без изменений.

## Контекст

ADR-007 ввёл «живой конверт» (`budget_envelope`): приход + горизонт, остаток не хранится, а
считается из фактических транзакций. Конверт один и целиком: он отвечает на вопрос «сколько
свободно осталось», но не на вопрос «сколько из этого на еду, сколько на транспорт».

Оператор хочет раскладывать приход по категорийным долям («еда», «транспорт», «развлечения»),
получать по ним остатки и уметь словами поправить одну долю. Лимиты долей должна назначать
система по истории трат, а не человек вручную.

## Решение

### 1. Именование: `share`, не `Bucket`

`Bucket` / `GroupByBuckets` в `internal/skills/budget/buckets.go` — уже занятый концепт:
группировка категорий для дайджеста (Обязательства / Цели / Жизнь и радость). Он **не трогается**.

Новый концепт называется **share** — доля прихода:

| Слой | Имя |
|---|---|
| Таблица долей | `budget_envelope_share` |
| Таблица категорий доли | `budget_envelope_share_category` |
| Таблица ручных правок лимита | `budget_envelope_limit_override` |
| Go-тип доли | `EnvelopeShare` |
| Go-тип правки | `EnvelopeOverride` |

Пользователю в ответах бота слово «share» не показывается — там остаётся «конверт».
Разделение только на уровне кода и схемы.

### 2. Лимиты назначает система, человек их правит точечно

Базовый лимит доли — **прогноз по переменным потребительским категориям** на длину горизонта
конверта. Источник истины для «что считать переменной ежедневной тратой» — существующая
`budget.IsVariableDailyExpense` (`internal/budget/categories.go`): потребительская И не
фиксированная. Основа расчёта — уже работающая `buildForecastBreakdown`
(`internal/skills/safetospend/compute.go:24`), она агрегирует прогноз по категориям
пропорционально `days/30`. Новая раскладка переиспользует её, а не заводит второй прогноз.

Оператор правит **отдельную долю словами** («на еду хватит 15000»). Правка сохраняется как
запись в `budget_envelope_limit_override` и **переживает пересчёт**: при перераскладке
базовый прогноз пересчитывается, override применяется поверх.

### 3. Делится `FreeAfterObligations`, не сырой приход

Раскладывается `FreeAfterObligations` из `computeSafeToSpend`
(`internal/skills/safetospend/compute.go`), то есть приход **после** вычета регулярных
платежей, долгов и плановых трат. Раскладывать сырой приход нельзя — доли бы конкурировали
с уже известными обязательствами и суммарно обещали больше денег, чем есть.

### 4. Инвариант сходимости — ТОЛЬКО на `allocated`

```
Σ allocated + свободно = FreeAfterObligations
```

`carried_in` в этот инвариант **не входит**.

Привязывать инвариант к существующему `RemainingTHB` (`computeRemaining`) **нельзя**: разница
между `Σ allocated` и `RemainingTHB` состоит из трёх независимых членов —

```
RemainingTHB − Σ allocated = −Σ carried_in + факт_фикс + факт_переменные_recurring
```

то есть перенос с прошлого конверта, факт по фиксированным категориям и факт по переменным
категориям, порождённый recurring-платежами. Ни один из них не является ошибкой раскладки,
поэтому равенство на `RemainingTHB` не сойдётся никогда и как инвариант бесполезно.

В ответе бота эти члены показываются явно, отдельными строками:

- **«вне конвертов»** = факт по фиксированным категориям + факт по переменным recurring;
- **«перенесено с прошлого раза»** = `carried_in`, своей строкой.

### 5. Recurring исключается из факта доли

Транзакции с `recurring_id IS NOT NULL` **не попадают** в факт по доле: они уже вычтены как
обязательства на этапе `computeSafeToSpend`, повторный учёт — двойной (ADR-007 §4).

Механизм тот же, что уже применён для дохода в `GetRegularMonthlyIncomeAvg`
(`internal/budget/store.go:855`): фильтр по `recurring_id` прямо в SQL-агрегате.

`consumptionSpentTHB` в `internal/skills/safetospend/remaining.go` (точнее — в `compute.go:123`,
вызывается из `remaining.go:47`) **не трогаем**: она обслуживает старый режим остатка ADR-007,
у неё своя семантика, и её правка сломала бы уже принятый оператором ответ.

### 6. Ключ категории: id + нормализованное имя, fallback обязателен

`budget_envelope_share_category` хранит **оба** ключа:

- `category_id UUID NULL` — FK на `budget_category`;
- `category_name TEXT NOT NULL` — в нижнем регистре.

Матчинг траты к доле: по `category_id`, если он есть; иначе по `lower(name)`.

Почему оба. Есть два класса транзакций, которые по id не матчатся:

1. транзакции с `category_id IS NULL` (`budget_transaction.category_id` — nullable, при удалении
   категории `ON DELETE SET NULL`);
2. регистровые дубли категорий: `FindCategoryByName` ищет по `LOWER(name)`, а уникальный индекс
   `idx_budget_category_name_type` — по `(name, type)` и регистрозависим, поэтому в таблице
   могут сосуществовать «Еда» и «еда» как разные строки с разными id.

Отсюда третье требование: **fallback-доля «прочее» обязательна всегда**. Всё, что не
смэтчилось ни по id, ни по имени, падает в неё. Без fallback часть факта потерялась бы молча.

### 7. Валюта: THB — единая расчётная

`allocated` и `carried_in` хранятся в THB, единой расчётной валюте проекта (как и весь
safe-to-spend). Приход конвертируется в THB **один раз**, при раскладке. Дальше пересчётов
курса нет — иначе остаток доли дрейфовал бы от движения курса без единой траты.

### 8. Остаток доли не хранится

```
remaining = allocated + carried_in − факт по категориям доли за период конверта
```

Хранение остатка запрещено — это инвариант недвойного учёта ADR-007 §4 в его структурном
виде: у каждого слагаемого ровно один источник, остаток всегда производен.

### 9. Carry-over по имени доли

- `kind = 'save'` — остаток **переносится** в новый конверт, ключ переноса — имя доли.
  Отсюда `UNIQUE(envelope_id, name)`: без него перенос по имени неоднозначен.
- `kind = 'spend'` — остаток **сгорает**.
- Доля с `kind='save'`, исчезнувшая из новой раскладки, всё равно создаётся: `allocated = 0`,
  `carried_in = остаток`. Иначе накопленное молча пропало бы вместе с долей.

### 10. Закрытие конверта: `period_end := now − 1 день`

При переключении на новый конверт старый закрывается как

```
period_end := now − 1 день
active     := false
```

Причина: все даты в схеме — `DATE`, а `periodSnapshotQuery` (`internal/budget/store.go:1273`)
фильтрует границы **включительно** (`>= period_start AND <= period_end`). При
`period_end := now` траты дня переключения попали бы одновременно в оба конверта — в старый по
верхней границе и в новый по нижней.

Если `period_end` при этом уходит раньше `period_start` (конверт заведён и закрыт в один день) —
обрезать до `period_start`, чтобы не получить период отрицательной длины (`GetPeriodSnapshot`
на таком возвращает ошибку).

### 11. Числа не проходят через LLM

Раскладка и остатки — **чистые функции** на Go. LLM только нарративит готовый результат.
Это прямое продолжение ADR-007: `computeSafeToSpend` / `computeRemaining` уже так устроены.

## Известное ограничение

У `budget_transaction` нет `chat_id` — факт по тратам глобальный, а конверт chat-scoped
(ADR-004). Значит доли считают факт по всем чатам сразу.

Скоуп сознательно **не расширяем**: у бота один пользователь, добавление `chat_id` в
транзакции — отдельная миграция с бэкфиллом всей истории и правкой всех агрегатов
(`advisorSnapshotQuery`, `periodSnapshotQuery`, forecast, digest). Цена не оправдана.
Ограничение фиксируется здесь, чтобы следующий агент не принял его за баг.

## Контракт роутинга (для golden-set)

| Сценарий оператора | skill | action |
|---|---|---|
| «пришло 127000, разложи по конвертам» | `budget` | `start_envelope` |
| «сколько в конвертах», «сколько осталось на еду» | `safe_to_spend` | — (read-only) |
| «на еду хватит 15000» | `budget` | `set_share_limit` |
| «купил еды на 3000» | `budget` | `add_expense` |

Последняя строка — не формальность: разграничение «правка лимита» vs «запись траты» уже
ломалось (simpleAI-399, simpleAI-q49). Обе фразы содержат категорию и сумму, различает их
только модальность. Кейс держится в golden-set как регрессионный.

Сценарии зафиксированы в `evals/golden_set.jsonl` (`r043`–`r047`) **до** кода.

**Где на самом деле живёт триггер.** Не весь роутинг задаётся Manifest'ом: в
`buildToolsSystemPrompt` (`internal/agent/router.go:18`) есть блок `ROUTING RULES` с пометкой
«приоритет выше описаний инструментов», и правило №2 хардкодит «купил / потратил / заплатил →
budget.add_expense». Проверено мутацией: вырезание триггеров `add_expense` из Manifest'а
budget-скилла **не** меняет маршрут для «купил кофе 200» — решает хардкод в роутере; а
вырезание `add_planned_expense` (триггер живёт только в Manifest'е) роняет кейс `r040` сразу.

Следствие для задач 6/8: разграничение `set_share_limit` vs `add_expense` («на еду хватит
15000» vs «купил еды на 3000») нельзя чинить одной фразой в Manifest'е — оно попадает в зону
действия `ROUTING RULES`, и правку надо делать там же, иначе она будет перебита.

## Поправка 2026-08-24 (simpleAI-faeq.10 / faeq.11)

Прогон на реплике и разбор оператором заставили изменить три решения выше.

### §3 отменён: делится приход, а обязательства — видимые конверты

`FreeAfterObligations` как «то, что делим» сохраняется, но обязательства больше
не исчезают из ответа. Каждый регулярный платёж из `budget_recurring` становится
долей `kind='fixed'` — со своим именем, суммой и датой платежа (`due_date`).

Причина — прямая: оператор отверг деление трат на «обязательные» и «на жизнь»
(«есть мне тоже надо, или ты считаешь что еда необязательна?»), а сводная строка
«обязательства 12332» ломала сходимость: приход визуально не сходился, и было
непонятно, куда делись деньги. Ресёрч подтверждает: у YNAB обязательные платежи —
первые КАТЕГОРИИ плана, а не вычет до раскладки.

Окно финансирования fixed-долей — месяц вперёд от начала периода, а НЕ период
конверта: аренда платится 10.09 при периоде до 06.09, но отложить надо сейчас
(sinking fund). Категорий у fixed-доли нет: её факт — сам recurring-платёж, а
транзакции с `recurring_id` в факт долей не попадают (§5 без изменений).

### §4: строка «вне конвертов» убрана

Она показывала 0 ฿ при аренде 18 000 и уборке 2 500 за период, потому что считала
ФАКТ прошедших трат, а читалась как «что ещё предстоит». Объяснять расхождение
отдельной сводкой больше нечем: каждый предстоящий платёж стоит своей строкой.

Инвариант §4 усилен и распространён на перенос:

```
Σ allocated + Σ carried_in  ≤  приход + реальный остаток прошлого периода
```

### §9: конверт, не проживший ни дня, переносит только свой carried_in

Повторная раскладка того же прихода в тот же день наращивала перенос
0 → 26681 → 53362 → 65335 THB. Конверт, закрытый в день создания (период нулевой
длины по §10), не прожил ничего: его `allocated` профинансирован тем же приходом,
который раскладывается заново, и переносить его — печатать деньги. Переносится
только его собственный `carried_in`.

Известное ограничение: второй НАСТОЯЩИЙ приход в тот же день неотличим от повтора
раскладки. Выбор сделан в пользу невозможности напечатать деньги.

### Новое: дневной лимит

```
лимит дня = (Σ гибких конвертов − потрачено) / оставшиеся дни
```

Приход в формуле не участвует — поэтому лимит работает и при приходе в 10 рублей,
и при нулевом. `fixed` и `save` в числитель не входят. Пересчитывается при каждом
показе остатков, то есть после каждой траты. Это зеркало, а не запрет.

### Новое: планка мелочи абсолютная

Порог схлопывания категории в «прочее» был долей свободных денег и двигался вместе
с обязательствами — «Транспорт 985» перепрыгивал его туда-обратно между
раскладками. Стал абсолютным (`minShareMonthlyTHB`, пропорционально длине периода):
набор конвертов — свойство трат человека, а не остатка после обязательств.

### Формат ответа

Обычный текст + ОДИН моноблок шириной 32 знака (порог 36 из ресёрча вёрстки
Telegram), две с половиной колонки: метка ≤18, дата платежа, сумма по правому
краю. Эмодзи внутри `pre` запрещены — ломают выравнивание. Разряды через пробел,
без копеек. Предупреждения «мало данных» свёрнуты в одну строку: одиннадцать строк
подряд прятали сам ответ.

### Разметка Telegram: `parse_mode=HTML` (решено, simpleAI-faeq.14)

Открытый вопрос «каким `parse_mode` слать» закрыт в пользу **HTML**, не MarkdownV2.

Причина — поверхность риска, а не вкус. Ошибка экранирования в Telegram не
портит вид сообщения, а роняет отправку целиком: API отвечает 400, и пользователь
не получает НИЧЕГО. В MarkdownV2 экранирования требуют восемнадцать символов,
включая точку и минус, — они есть буквально в каждом сообщении с датой и суммой,
и часть текста пишет LLM, то есть перечислить источники символов заранее нельзя.
В HTML опасных символов три: `&`, `<`, `>`. Обе нужные конструкции — `<pre>` для
моноблока и `<b>` для заголовков — покрыты.

Как устроено (`internal/bot/format`):

- Скиллы продолжают писать в ограниченной разметке (моноблок в тройных кавычках,
  `**жирный**`). Это **структура намерения**, а не готовый Markdown.
- Рендер переводит её в HTML, экранируя ВСЁ остальное. Постфактум-экранирование
  готовой разметки отвергнуто: оно требует отличать «звёздочку-разметку» от
  «звёздочки из текста LLM» — ровно тот класс ошибки, который роняет отправку.
- Непарный ограничитель и непарные `**` остаются литералом: незакрытый `<pre>` —
  это 400.
- Длинный текст режется по лимиту Telegram, разрез закрывает и переоткрывает `<pre>`.
- Если Telegram всё же ответил ошибкой на размеченный вариант и не ушло ещё
  ничего — тот же текст уходит простым. Молчание бота хуже звёздочек в чате.

Разметка включается в ЕДИНСТВЕННОЙ точке отправки каждого канала — в адаптере
(`internal/adapters/telegram`) и в пуше (`internal/notify/telegram.go`). Оба
канала везут одну и ту же раскладку конвертов; починка одного из них оставила бы
утренний пуш без разметки.

## Последствия

- Схема растёт на три таблицы; миграции — вперёд, без правки `00016_budget_envelope.sql`.
- `budget_envelope` получает доли; старый режим остатка ADR-007 продолжает работать как был.
- Новый action `budget.set_share_limit` расширяет манифест budget-скилла — а значит меняет
  `prompt_hash` в eval-прогонах. Регрессию по существующим кейсам ловит golden-set.
