# ADR-021: Окно — бизнес-сущность со своей таблицей

- **Статус:** Accepted (решение владельца 2026-11-08)
- **Дата:** 2026-11-08
- **Заменяет:** ADR-020 §2 (таблица правок длины `plan_window_length`); уточняет ADR-009 R1 и ADR-019 («окна
  вычисляются, не хранятся» больше не верно для начавшихся окон).

## Контекст

После ADR-020 в базе лежали только правки длины, а сами окна каждый раз вычислялись из поступлений. Владелец считает
окно бизнес-сущностью: у него есть даты, его правят и удаляют, и оно не должно меняться само, когда меняются
поступления.

## Решения владельца
1. Окно появляется само, когда приходит или планируется зарплата/аванс вне окон.
2. У окна можно двигать и начало, и конец; окно можно удалить. Окна не пересекаются.
3. Если зарплату окна удалили или перенесли, окно остаётся. Поступления и платежи относятся к окнам по дате.

## Решение

### 1. Таблица
`plan_window (id, chat_id, start_date, end_date, deleted, created_at, updated_at)`; длина 1..62 дня (CHECK);
одно действующее окно на дату начала в чате (частичный уникальный индекс). Удаление — пометка `deleted`: на этих
датах окно само больше не появится. Запись — в первый чат области, правка и удаление — по всей области. Миграция
00032 переносит правки из `plan_window_length` в окна и удаляет ту таблицу; откат возвращает её из окон
нестандартной длины.

### 2. Когда окно сохраняется
Будущее окно, которое открыла ожидаемая зарплата (в том числе из регулярного платежа), остаётся расчётным: правка
правила повтора должна его двигать. В **день начала** окно сохраняется (`Service.load` → `materialize`) и дальше
от поступлений не зависит. Правка будущего окна сохраняет его сразу. Без хранилища (`WithWindowStore` не подключён)
окна, как раньше, только считаются.

### 3. Построение окон (`BuildWindows`)
Сохранённые окна (включая удалённые) — история, от начала первого до конца последнего. Новые расчётные окна
(14 дней) открываются зарплатами вне истории: **после её конца** — как раньше; **до её начала** — только если все
14 дней окна помещаются до первого сохранённого окна (так окна до выкатки считаются и сохраняются при первом чтении,
а не сливаются с перенесённым окном). Зарплата внутри сохранённого окна идёт в него; зарплата внутри истории вне окон
(в зазоре, чуть раньше сдвинутого начала, на датах удалённого окна) окно не открывает и ведёт себя как обычный приход
(ADR-019: в окно по дате) — иначе сдвиг начала или удаление окна тут же порождали бы рядом новое окно. Правило «окон
нет — первое поступление открывает окно» действует, только когда истории нет: удалённое окно само не воскресает.
Пересекающиеся сохранённые окна (разные чаты области) не роняют расчёт: остаётся раннее.

### 4. Команды
`Service.CurrentWindow / ResizeWindow / SetWindowEnd / SetWindowStart / DeleteWindow` над окном на экране за портом
`WindowStore` (ISP). Правила: длина 1..62; конец не раньше сегодня (`ErrWindowEndPast`); без пересечения с другими
сохранёнными окнами (`ErrWindowOverlap`); удалить окно можно, только если после этого на экране останется окно
(`ErrLastWindow`: удаление примеряется на тех же поступлениях) — иначе править было бы нечего. Будущее (расчётное)
окно при правке сохраняется сразу с новыми датами, одной записью. Отдельного «вернуть 14 дней» нет (ADR-020).

### 5. Интерфейсы
- Веб: `POST /api/plan/window/resize`, `PUT /api/plan/window/end`, `PUT /api/plan/window/start`,
  `DELETE /api/plan/window`; в строке окна «−1/+1 день», «с», «до», «удалить окно» (с подтверждением).
- Бот и агенты: навык `plan_window` (extend / shrink / set_end / set_start / delete / show), правило маршрутизации 9,
  golden-кейсы r061–r066.

## Последствия и риски
- Первое чтение плана после выкатки сохранит все начавшиеся окна истории (по одному на ~2 недели).
- Поступление, внесённое задним числом в зазор между сохранёнными окнами, окно не откроет — попадёт в следующее
  окно по дате. Нужное окно владелец создаёт сдвигом дат соседнего.
- Лимиты и платежи «в окно» ищут окно как первое с концом не раньше своей даты (`ResolveWindow`) — сдвиг начала их
  не теряет.
