# ADR-010: Категории — единая точка создания, слияние, алиасы, журнал

- **Статус:** Accepted
- **Дата:** 2026-10-17
- **Контекст эпика:** simpleAI-nebf (GitHub #80, #78; simpleAI-lsx5, simpleAI-ck5r)
- **Дополняет:** ADR-008 (доли конвертов хранят `category_name`)

## Контекст

В проде 34 категории расходов с смысловыми дублями (Еда/продукты/продукт, Одежда/clothes,
Здоровье/health). Категории создаются в трёх местах (`skills/budget/transactions.go` ~40 и ~83,
`recurring.go` ~39) через отдельные `FindCategoryByName` и `AddCategory`; индекс `(name,type)`
регистрозависим, поэтому «Кофе» и «кофе» вставляются оба. На категорию ссылаются четыре таблицы:
`budget_transaction`, `budget_recurring`, `budget_planned_expense` (все `category_id`, SET NULL) и
`budget_envelope_share_category` (`category_id` без ON DELETE и `category_name` в нижнем регистре).

Владелец отверг одноразовый SQL-скрипт слияния: слияние должно быть частью постоянного модуля.

## Решение

### 1. Пакет `internal/categories`
Отдельный пакет, не `internal/budget` (там `store.go` уже 1500+ строк). Зависит от узких интерфейсов
(ISP), реализация над БД подключается снаружи:
`Source` (список категорий), `Normalizer` (ключ сравнения), `SimilarityFinder` (кандидаты в пары),
`Decider` (слить, оставить, отложить), `Merger`, `Rollbacker`, `Journal`, `Notifier`, `Resolver`,
`Deduplicator` (оркестратор). Новая стратегия поиска или решающий (LLM-судья позже) добавляются
без правки остальных. `TxRunner` даёт Merger и Journal одну транзакцию.

### 2. Единая точка создания
`Resolver.GetOrCreate(name, type)`: нормализация → поиск по алиасу (если имя алиас, вернуть целевую) →
`INSERT ... ON CONFLICT (lower(name), type) DO NOTHING RETURNING` → при пустом результате SELECT.
Прямой `AddCategory` вне пакета запрещён. Ошибка создания больше не проглатывается (в `recurring.go`
сейчас `if err == nil`): поведение осознанно строже.

### 3. «Удаление» = слияние + алиас
Жёсткого удаления судьёй или дедупликатором нет. Merge(source→target) в **одной транзакции БД**:
блокировка обеих строк `FOR UPDATE` в порядке id; проверка, что type совпадает; перенос ссылок
в четырёх таблицах (+ пятая, `plan_category_limit`, ADR-011: при конфликте ключа остаётся лимит цели, лимит источника уходит в журнал со снимком), при этом у долей `category_id` и `category_name` меняются **вместе**
(дубль по PK `(share_id, category_name)` схлопывается); перенаправление алиасов, смотревших на source,
на target (цепочек нет); новый алиас `source → target`; записи в `category_merge_log` и
`category_decision_log`; `DELETE` source. Алиас не может совпадать с именем живой категории.
Старое имя остаётся синонимом, поэтому классификатор не создаст его снова (разрыв петли
«создать → слить → создать»).

### 4. Журнал и откат
`category_merge_log` получает `merge_id` и снимок удаляемой категории (имя, type, icon, sort,
старое `category_name` доли, `rolled_back_at`). Rollback восстанавливает категорию **с прежним id**,
возвращает строки по `row_id`, удаляет алиас. Откат запрещён для строк без `merge_id` (журнал
первого ручного прогона), если цель уже удалена или строка менялась после слияния.

### 5. Оповещение после commit
`Notifier` вызывается только после коммита; ошибка оповещения не откатывает слияние (доставка не
зависит от записи, как в других пайплайнах).

### 6. Первый срез без LLM
Правила и карта синонимов (`clothes→Одежда`, `health→Здоровье`, `продукт/продукты→Еда`) плюс
нормализованное равенство. Неоднозначные пары не сливаются, а уходят в `category_review_queue`.
Дедупликатор обязан иметь `--dry-run` (таблица «до/после» по суммам) и идемпотентный `--apply`.

### 7. Миграция 00022
Идемпотентна: `CREATE TABLE IF NOT EXISTS`, `ADD COLUMN IF NOT EXISTS`. Состояние прода
неизвестно (`category_merge_log` создана вручную скриптом, без `merge_id`). Если в проде есть пары
категорий, различающихся только регистром, миграция сначала сливает их простым SQL с записью в
журнал (единственный допустимый одноразовый SQL: без этого уникальный индекс не создать).
Reconcile `category_name` долей делается в Go первым шагом первого прогона, не в миграции.

## Отвергнутые варианты
- **Одноразовый SQL-скрипт** слияния: решение владельца.
- **Мягкое удаление** (`archived_at`, `merged_into`): все читатели (`ListCategories`, план, прогноз)
  пришлось бы фильтровать, blast radius L. Выбран DELETE со снимком в журнале.
- **Код в `internal/budget`**: пакет уже перегружен.

## Последствия и риски
- Слияние мгновенно меняет экран «Как обычно тратишь»: dry-run показывает суммы до и после.
- `lower()` в Postgres зависит от collation (проверить `SHOW lc_ctype`); ключ сравнения считается
  одинаково в БД и Go, языковые синонимы ловятся только картой и алиасами.
- Переименование категории тоже идёт через модуль (обновляет `category_name` долей и ставит алиас);
  прямой `UPDATE name` запрещён.
- Гонка Merge и записи новой траты: Resolver идёт через алиасы, FK-ошибка записи повторяется один раз.
- Предусловие P0 (делает владелец, чтение): `SELECT count(*) FROM budget_category WHERE type='expense'`,
  `\d category_merge_log`, доли с `category_id`, не совпадающим с `category_name`.
