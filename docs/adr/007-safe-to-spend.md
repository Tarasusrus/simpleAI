# ADR-007: Safe-to-Spend / живой конверт

**Дата:** 2026-07-23
**Статус:** Accepted
**Issues:** simpleAI-l960 (spike/дизайн)
**Связанные ADR:** ADR-001 (Forecast), ADR-002 (LLM-reasoning skills), ADR-003 (eval-suite), ADR-004 (stateful memory)

---

## Context

Владелец хочет флоу: пишет боту **приход** (сумма + период) → бот из накопленной
статистики отвечает, **сколько реально свободно** на период после всех известных
и плановых обязательств, и распределяет приход. Профит: «все планы в голове не
удержать». Индустриальный аналог — Safe-to-Spend (банк Simple) + envelope /
zero-based budgeting.

Эмпирический прогон текущего бота (botclient на реплике, deepseek) вскрыл 4 бага:

1. **Роутинг-мутация.** «Пришло 127000, сколько свободно?» → `budget.add_income`:
   бот ПИШЕТ приход в ledger вместо ответа. В проде засоряет данные при каждом
   вопросе.
2. **«Свободно» не привязано к приходу.** Отдаётся `Фонд Да = −76014₽`, который
   не учитывает названную в сообщении сумму.
3. **Якорь дохода загрязнён.** `GetMonthlyIncomeAvg` берёт все income-строки;
   разовые поступления (Март «Прочее» 126000, Апрель без категории 152126)
   раздувают среднее ~123k→~193k (+57%).
4. **Нет примитива safe-to-spend.** Приход из сообщения + произвольный период →
   детерминированный свободный остаток отсутствует.

Существующее: `AdvisorSnapshot.FreeCash = BalanceMTD − UpcomingRecurring −
ActiveDebtDue` (THB, **month-scoped** CTE), `GetForecastData`, AdvisorSkill
(advice/analyze, ADR-002). Снапшот привязан к календарному месяцу — произвольный
период не покрыт.

## Decision

### 1. Модель хранения — H3 «виртуальный конверт», остаток производный

Приход-событие + период + план-раскладка хранятся тонкой сущностью. **Свободный
остаток НЕ хранится** — вычисляется на лету из фактических транзакций за период.
Это структурно исключает двойной учёт (единственный источник истины — транзакции)
и иммунно к правкам трат задним числом. Цена — пересчёт на запрос; при текущем
объёме (ADR-001 <50ms) неважно.

Отвергнуто **H2** (хранимый decrement-баланс): дублирует то, что уже считают
транзакции/FreeCash → двойной учёт + рассинхрон; и `EnvelopeSkill` с записью
нарушил бы ADR-002.

### 2. Фазовость: H1 (stateless) → H3 (конверт)

**Фаза 1 = H1**, stateless: приход берётся из сообщения, ничего не пишется,
свободный остаток считается из существующих срезов (расширенных на период).
Обкатывает детерминированную математику и формат до персистентности. H3
(персистентный конверт + ручной ввод плановых трат) — последующие фазы.

### 3. Инвариант: LLM не считает арифметику

Свободный остаток и раскладка считаются **детерминированно в Go**. LLM только
нарративит. Проверяется тестом: числа не проходят через LLM (мутация LLM-ответа
не меняет числовой вывод).

### 4. Инвариант: нет двойного учёта

Остаток конверта == период-агрегация фактических транзакций; не дублирует
FreeCash/forecast/обязательства. Формально: `свободно = приход −
известные_обязательства(период) − уже_потраченное(период)`, где каждое слагаемое
берётся ровно из одного источника.

### 5. Граница CRUD / reasoning (amendment к ADR-002)

- **Safe-to-Spend reasoning** — новый **read-only plugin** `SafeToSpendSkill`
  (`internal/skills/safetospend/`), профиль ADR-002 (2+ источника + LLM-нарратив,
  stateless, не зовёт другие skill'ы, явный negative-prompt).
- **Приход НЕ записывается** (фикс бага №1): reasoning-skill принимает сумму из
  сообщения и НЕ вызывает `add_income`. Роутинг «пришло X, сколько свободно?» →
  `safe_to_spend`, а не `budget.add_income`.
- **Персистентность конверта и ручных плановых трат** (H3) — CRUD-actions внутри
  `BudgetSkill` + новые сущности в `Store` (chat-scoped). Reasoning и CRUD не
  смешиваются в одном plugin'е.

### 6. Мультипериодная агрегация в Store

Новый метод `Store` принимает произвольный период (from/to), chat-scoped,
возвращает доходы/расходы/обязательства за период в THB. Не ломает существующий
MTD-путь снапшота.

### 7. Классификация прихода — детерминированный дефолт

Разовый vs регулярный определяется **детерминированно** (совпадение суммы/периода
с recurring income → регулярный; иначе разовый), LLM может лишь предложить.
Ошибка классификации не должна искажать арифметику периода.

### 8. Чистка якоря дохода (фикс бага №3)

Для baseline/forecast среднего дохода исключать разовые поступления: income с
`recurring_id IS NULL` и категорией из denylist (`Прочее`, без категории) не
входят в «регулярный доход». Отдельный метод/флаг в `Store`; `GetMonthlyIncomeAvg`
не менять по месту (используется в affordability) — вводить чистый вариант.

### 9. chat_id-изоляция и валюта

Новые сущности (H3) — chat-scoped, изоляция chat A≠B как тест-инвариант (ADR-004).
Все суммы приводятся к THB через существующую конверсию; приход в RUB, часть
обязательств в THB — конверсия обязательна.

## Consequences

**Плюсы:** структурная защита от двойного учёта; фикс 3 из 4 багов уже в H1;
переиспользование FreeCash/forecast; предсказуемая декомпозиция.

**Минусы:** остаток — производная (пересчёт на запрос); H1 не закрывает ручной
ввод плановых трат → полный эталон (27800₽ после 7 известных трат) достижим
только с фазой planned_expense; риск routing-конкуренции `safe_to_spend` vs
`advisor.advice`/`budget.summary` → нужен negative-prompt + smoke/eval.

**Действия (декомпозиция эпика, 6 задач):**
0. ADR-007 (этот документ).
1. Мультипериодная агрегация в `Store` (произвольный период, chat-scoped) + юнит-тесты границ.
2. H1 `SafeToSpendSkill` (read-only plugin): приход из сообщения, детерминир. остаток, LLM-нарратив; фикс роутинга (бага №1/№2).
3. Детерминированная классификация прихода + чистка якоря дохода (бага №3).
4. H3 persistence: миграция `budget_envelope` (income_event + период + план), CRUD в BudgetSkill/Store, chat_id-изоляция.
5. Производный остаток «сколько свободно осталось» + проверка недвойного учёта против FreeCash.
6. `planned_expense` (ручные разовые плановые траты) + eval-сьют (ADR-003) против эталона 127k→27800.
