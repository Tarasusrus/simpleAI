# ADR-015: Траты без лимита, планирование из траты и список трат категории

- **Статус:** Proposed (правки по ревью architect внесены, ждёт подтверждения владельца)
- **Дата:** 2026-10-23
- **Контекст:** макет «Лимиты: траты без лимита» (4 экрана), ревью UX, наблюдения на живом экране плана.
- **Дополняет:** ADR-011 (лимиты категорий), ADR-013 (§7 ниже). **Не меняет:** формулу ADR-011 §3.
- **Связи:** ADR-009 (план окна), ADR-010 (категории), ADR-012 (единая дверь категорий), ADR-013
  (таксономия еды: «Продукты»/«Рестораны», лимит «Еды» переезжает на «Продукты»). Номер 015: 012–014 заняты.
- **Независим от:** ADR-008 (конверты-доли прихода).

## Контекст

Наблюдения на живом экране (окно 21.10–03.11):

1. Лимит стоит на «Продукты», а основная еда лежит в «Еде»: «Еда» 4 865 ₽, «Рестораны» 2 779 ₽,
   «Продукты» 1 163 ₽ за текущее окно. Лимит почти не ловит реальные траты на еду.
2. Траты из бота («поход в кафе», «продукты», «сок») показываются в общем списке без категории и
   без «изменить». Увидеть траты одной категории нельзя.
3. Категория без лимита на экране не появляется. Владелец не получает повода спланировать деньги.
4. Строка «Продукты» в блоке «Лимиты» (с ↻) и строка «Продукты» в «Как обычно тратишь» — одна
   категория в двух блоках. Дубля категории нет (диагностика на проде желательна, см. «Проверки»).

Владелец хочет видеть лимит не как запрет, а как инструмент планирования: после траты (поездка на
такси) сразу решить, сколько отложить на оставшиеся траты категории в окне. Цель: со временем все
траты разложены по лимитам, владелец правит свои лимиты.

## Решение

### 1. Принцип
Лимит — план, а не запрет. Ограничений на траты нет, перерасход ничего не блокирует (ADR-011 §1).
Слово «лимит» остаётся в блоке «Лимиты». Новое действие называется «Запланировать».

### 2. Формула не меняется, «без лимита» определено
`CanSpend = income − Payments − Spent − Reserve − LimitHold` (ADR-011 §3, `calc.core()` в
`internal/plan/compute.go`). `Spent` включает все оплаченные факты окна, поэтому трата в категории
без лимита **сразу уменьшает «Свободно»**; трата в категории с лимитом съедает остаток лимита, и
деньги не считаются дважды (вычитается `max(лимит, потрачено)`).

«Категория без лимита» = **нет лимита, действующего на это окно** (`limitsFor()`), а не «нет строки
в `plan_category_limit`»: разовый лимит прошлого окна или повторяющийся со стартом в будущем
категорию без лимита не делают.

`UnplannedSpent` = Σ оплаченных трат окна (в валюте показа, через `c.money`) в категориях без
действующего лимита, исключая `Category == ""` («Без категории») и факты с `RuleID` (платежи
повторяющихся правил — это обязательства, не «вне плана»). Считается **только в `calc`**, рядом с
`limits()`, из той же выборки событий; во фронте и в `web` не дублируется. В формулу не входит.
Инвариант для теста — непересекающееся разбиение оплаченных фактов окна: `Spent = Σ(факты с
RuleID, любая категория) + Σ(факты без RuleID и без категории) + Σ limit.Spent + UnplannedSpent`,
где последние два слагаемых — факты без `RuleID` с категорией (с действующим лимитом / без него).

Текст в шапке: «В том числе N ₽ потрачено вне плана». Он называет часть «Свободно», не объясняет
весь расход: платежи правил и «Без категории» в строку не входят.

### 3. Блок «Не запланировано · N»
Под «Лимитами». Строка на каждую категорию без действующего лимита с оплаченными тратами окна:
имя, сумма, бирка «без плана», стрелка раскрытия. Нейтральный стиль (не предупреждение). При 3 и
более категориях показываются две с наибольшей суммой, остальные «ещё N». Пустой блок не
показывается. Категорию можно скрыть («Не планировать»); скрытые — по ссылке «Скрытые · N».
Хранение: `plan_category_dismissed (chat_id, category_id REFERENCES budget_category(id) ON DELETE
CASCADE, created_at)`, `UNIQUE (chat_id, category_id)`, миграция 00027 (00025 и 00026 заняты ADR-013). Запись по `ChatIDs[0]` (как
`AddLimit`), чтение по всем `ChatIDs` области. Слияние категорий: флаг скрытия источника
теряется (допустимо, решение зафиксировано), каскад не блокирует `cmd/categories`. Down — `DROP
TABLE IF EXISTS` без защиты (данные некритичны). Миграция аддитивная.

### 4. Предложение суммы
Сумма подсказки не меняется: `AvgCount × AvgAmount = sum/months` (ADR-011 §4). Нового — только
`AvgCount` и текст «Это трата 1 из примерно N». `AvgAmount` отдельно не вводится. Нужен **новый
запрос с `COUNT(*)`** по тем же фильтрам, что `PlanLimitHistory` (он отдаёт только `SUM`),
возвращающий и число трат за месяц; поле `AvgCount` добавляется в `plan.LimitSuggestion`. Число трат
категории в текущем окне берётся из событий окна в `plan`, не из истории. Считать в THB.
Исправить в `PlanLimitHistory`: `COALESCE(c.name,'Прочее')` склеивает «без категории» с «Прочее» и
завышает историю «Прочего».
- История ≥ 2 полных месяцев: «Это трата 1 из примерно N за окно».
- Уже было N или больше трат: «Это уже k-я, обычно N».
- История < 2 месяцев: цифр нет, текст «Распределить деньги на эту категорию?». Предзаполнять
  «фактически потрачено» нельзя: лимит `L ≤ S` даёт `LimitHold = max(L−S,0) = 0`, и «Свободно после
  плана» показывало бы A → A. Предзаполнение = 2 × потрачено в окне (ещё столько же на остаток окна),
  владелец правит сумму; «Свободно после плана» при этом уменьшается на потраченное, A → A исключено.
- Нет курса: подсказки нет.

### 5. Действие «Запланировать»
Использует `AddLimit` и `PreviewLimit` (ADR-011): сумма редактируется, рядом «Свободно после плана:
A → B ₽» из `PreviewLimit`. «Повторять каждое окно» — галочка, по умолчанию выключена. Окно лимита
— текущее (`limitWindow()` → `chosenWindowStart(WindowCurrent)`); эндпоинт §6 берёт то же окно.
- **`POST /api/plan/limits` возвращает `id`** созданного лимита (изменение контракта и тест).
- **Отмена:** тост «Запланировано … · Отменить» удаляет лимит по `id`; «не найден» считается успехом.
  Если лимит успели изменить (другая вкладка, `PUT`), удаляется изменённый: это принято и описано в
  интерфейсе («Отменить» действует, пока тост на экране). Для повторяющегося лимита «Отменить» в
  тосте не показывается (иначе молча уйдёт план на будущие окна); удаление — через правку лимита.
- Лимит на «Без категории» запрещён (ADR-011 §1). Дубли ловят индексы `uq_plan_category_limit_*`.

### 6. Траты внутри категории
Стрелка раскрывает строку категории (в «Лимитах» и в «Не запланировано»). Внутри: траты окна
(дата, название, сумма, страница 20 строк), «Показать все траты категории», блок «Впереди в
категории». Платежи в «Ближайших» остаются на месте.
- Эндпоинт `GET /api/plan/categories/transactions?category=…&cursor=…` под `s.auth` и тем же флагом,
  что лимиты (без флага — 404). Окно определяет **сервер**, то же, что на экране.
- Источник: оплаченные факты окна **без `RuleID`**, тот же ключ категории — сумма строк равна `Spent`
  строки категории. «Без категории» (`category_id IS NULL`) — запрещено, 400.
- Категория резолвится в `category_id` одним запросом (`type='expense'`), дальше фильтр по
  `category_id`, не по имени; паритет `lower(trim())` в Go и SQL проверяется тестом (кириллица,
  регистр). Алиасы не используются. Фильтр по `ChatIDs`.
- Пагинация keyset по `(transaction_date, id)`, размер 20 на сервере, ответ с `hasMore`, сортировка
  `date DESC, id`. На проде проверить `EXPLAIN`.
- «Впереди в категории»: неоплаченные плановые платежи категории в окне, включая повторяющиеся
  правила (по смыслу «впереди»), но с пометкой; в `Planned` лимита они не входят (ADR-011 §3).

### 7. Категории еды — по ADR-013
Таксономию еды («Продукты», «Рестораны», «Еда» как легаси, перенос лимита «Еды» на «Продукты»,
алиасы, два этапа разнесения истории) решает **ADR-013**; этот ADR её не повторяет и не меняет.
Что важно для функций ADR-015:
- Блок «Не запланировано» показывает «Рестораны» как категорию без лимита (решение владельца
  ADR-013: лимит один и только на «Продукты»). Для неё действие «Запланировать» предлагается, но не
  навязывается; «Не планировать» скрывает её (§3) — ожидаемый ответ владельца.
- Пока история в «Еде» (до этапа 2 ADR-013), «Еда» остаётся в «Лимитах»/«Не запланировано» по общим
  правилам; подсказка суммы для «Продуктов» молчит до 2 полных месяцев (ADR-013, последствия).
- `DefaultSynonyms`, алиасы и сиды не трогаются здесь: они в ADR-013 (§3, §5, миграция 00026).

### 8. Выкатка
Backend (поля DTO, эндпоинты, 00027) → фронт за флагом. Новые поля DTO обратно совместимы. Данные
категорий (§7) — отдельный релиз и отдельная операция, не завязанная на фронт.

### 9. Одно ядро лимитов для всех интерфейсов (требование владельца, 2026-10-23)
Лимиты принадлежат ядру (`plan`), одинаковы для веба и бота; расхождение недопустимо. Сейчас их
два независимых источника: веб читает `plan_category_limit` (ADR-011), а бот считает «лимит» из
конвертов-долей (`internal/skills/safetospend/compute.go`: `limit := sh.Allocated + sh.CarriedIn`,
ADR-008). ADR-011 §5 сознательно отложил объединение («бот — будущий потребитель лимитов плана
через `plan.Service`»). Этот ADR объединение **не выполняет**, но фиксирует, что оно обязательно
и что новые функции ADR-015 (`UnplannedSpent`, «Запланировать», трата внутри категории) обязаны
идти через `plan.Service`, чтобы бот мог читать их без второй реализации. Дизайн объединения
(бот читает `plan.Service`; судьба `budget_envelope_share*`; миграция данных) — отдельный ADR-016 с
вердиктом architect; до него новые лимиты не дублируются в боте и не пишутся в `budget_envelope_share*`.

## Проверки до реализации
- Read-only на проде: `SELECT id,name,type,encode(convert_to(name,'UTF8'),'hex'),length(name) FROM
  budget_category WHERE name ILIKE '%продукт%' OR name ILIKE '%еда%' OR name ILIKE '%рестор%';` и
  алиасы Еды: `SELECT * FROM budget_category_alias WHERE category_id = (id «Еды»);`.
- Сколько трат за окно приходится на «Еду», «Продукты», «Рестораны».

## Решение владельца (2026-10-23)
«Свободно» уменьшают и фактическая трата, и лимиты; главное — не считать деньги дважды (§2 это
обеспечивает). Блок «Не запланировано» — очередь на разнесение, а не постоянный раздел.

## Ограничения (известные)
- Предложение «1 из N» зависит от истории; при сезонности и выбросах неточно (как ADR-011 §4).
- Скрытие — свойство чата, не окна; при слиянии категорий флаг теряется.
- История «Еды» не разносится: «Обычно» у «Продуктов» и «Рестораны» занижено до накопления данных.
- «Отменить» после правки лимита в другой вкладке удалит уже изменённый лимит.

## Декомпозиция (по вердикту architect, после правок — YES)
1. `plan`: `UnplannedSpent` и список категорий без действующего лимита в `calc`; инвариант `Spent`
   property-тестом; DTO.
2. Миграция 00027 `plan_category_dismissed`, порт скрытия/возврата, учёт в `merge.go`.
3. `LimitSuggester`: `AvgCount`, новый запрос с `COUNT`, ветки «мало данных» и «уже N-я», правка
   «Прочего».
4. Читатель и `GET /api/plan/categories/transactions` (keyset, окно сервера, `EXPLAIN`).
5. `POST /api/plan/limits` возвращает `id`.
6. Фронт: блок «Не запланировано», раскрытие, форма «Запланировать», тост отмены.
7. (Закрыта как дубль ADR-013: симметричные задачи simpleAI-44qa, ik8f, 2lh6, uxcl.)
8. (Вне эпика) разнесение истории «Еды» — этап 2 ADR-013.
